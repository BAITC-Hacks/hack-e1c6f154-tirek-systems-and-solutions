# Регулярный спрос: доступность, клиентские заказы и переобучение

Офлайн-прогноз по публичному наблюдаемому входу `forecast-input-v2` из
`model/testbed/adapters.py`. `forecast(request)` возвращает дневные числа по каждому
SKU. `forecast_with_audit(request)` дополнительно возвращает метод, оценки прошлых
окон, экспозицию и исключённый клиентский объём. Генератор, seed, скрытый спрос и
будущие наблюдения модели не передаются; неизвестные поля отклоняются.

На каждом запуске коэффициенты заново оцениваются по переданной актуальной истории.
Это пересчёт при вызове функции, без фоновой интеграции с ERP или автоматического
изменения бизнес-правил. Обучение на реальных партнёрских данных и сохранённые веса
находятся в отдельном `model/forecast_v2/`; этот модуль решает задачу регулярного
спроса при наличии доступности и обезличенных клиентских событий.

## Методы и выбор

Сравниваются средние за 56/182 дня, недельный календарь за 365 дней, календарь с
трендом за 182 дня, годовая гармоника с трендом и неделей за 560 дней, а также
медиана полного горизонта по прошлым окнам. Регрессия — регуляризованная Poisson
GLM, коэффициенты находятся IRLS; доступная доля дня и известная промоакция входят
в экспозицию. Среднее без дополнительных признаков вычисляется аналитически.

Для каждого SKU выбор использует до трёх завершённых прошлых 28-дневных окон.
Тренировочная часть каждого окна очищается повторно на свою дату. Результаты
исторических окон сравниваются с ретроспективно очищенной оценкой наблюдавшихся
продаж; это не подтверждённая истина о потерянном спросе. Неполные наблюдения
не участвуют ни в экспозиции, ни в оцениваемом целевом объёме.

Медиана горизонта оптимизирует абсолютную ошибку, поэтому выдачу нельзя целиком
называть математическим ожиданием. Дневная раскладка медианы равномерна. Для
закупки по квантилям нужны отдельно проверенные совместные сценарии; точечный
прогноз не заменяет распределение. Интеграционные тесты с единственной траекторией
обозначены как детерминированные примеры.

## Клиенты и отсутствие товара

Крупные покупки группируются в скользящие семидневные окна по клиенту и SKU.
Аномальным считается превышение обычного недельного клиентского объёма больше
восьми типичных положительных дневных продаж товара. Повторяемый крупный клиент
сохраняется; разовый избыток у постоянного клиента тоже проверяется. Нулевые события
не подтверждают повторяемость. Пересекающиеся окна не исключают одну продажу дважды.
Это объяснимая эвристика кандидата на проектный спрос, а не доказанная классификация.
Нужно подтверждение на реальных клиентских данных; исходные события не удаляются.

Дни нулевой доступности не становятся доказанным нулевым спросом. При недостаточной
экспозиции используется явно переданный аналог категории. Если нет ни доступных
наблюдений, ни аналога, функция требует данные, а не возвращает фиктивный ноль.
Предполагается, что доля доступности корректно описывает экспозицию спроса. При
пропадании товара именно в пиковые часы такая поправка может быть смещена; в реальных
файлах партнёра точной дневной доступности и клиентских ID сейчас нет.

## Проверка

Из корня репозитория, Python с `model/requirements.txt`:

```sh
python -m unittest model.regular_forecast.test_predictor model.decision.test_integration -v
python -m model.testbed.run evaluate --split development --adapter model.regular_forecast.predictor:forecast --output /tmp/regular-development
```

Финальная проверка требует отдельной заморозки кода/протокола до просмотра финальных
seeds; команды и результаты записываются в общем отчёте. Демонстрационный business
calculator среды не является расчётным модулем `model/decision`; его показатели
не подменяют интеграционные проверки. Синтетическое качество не доказывает качество
на реальных данных, а доля успешных бизнес-тестов не является точностью прогноза.
