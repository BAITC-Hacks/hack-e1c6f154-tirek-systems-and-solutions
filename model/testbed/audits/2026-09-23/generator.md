# Аудит генератора и границы данных — 2026-09-23

раскрывает скрытую историческую классификацию покупки; **GEN-02 / medium** —

Проверены все 12 сценариев, seeds **101, 202, 303**, оба origin: **72 кейса / 288 SKU**.
Final seeds этим probe не генерировались. Прочитаны `generator.py`, `adapters.py`,

## GEN-01 — high: идентификатор содержит скрытую классификацию

Точные места: `model/testbed/generator.py:129` — суффикс `0` для обычного события;
`model/testbed/generator.py:132` — суффикс `1` для регулярного крупного клиента;
`model/testbed/generator.py:138` — суффиксы `2..6` для проекта.
Это противоречит комментарию `generator.py:126` и обещанию документов без метки
«проект» в `model/testbed/README.md:56`. Существенно для MH4
(`docs/requirements-matrix.md:24`) и DEMAND-02 (`docs/decision-rules.md:26`).

Ожидалось: непрозрачные ID событий, по которым нельзя восстановить скрытый тип
покупки без анализа клиента, дат, объёма и повторяемости. Фактически достаточно:

```python
project_event = int(event['event_id'].rsplit('-', 1)[-1]) >= 2
recurring_event = int(event['event_id'].rsplit('-', 1)[-1]) == 1
```

Сравнение декодера со скрытым проектным ledger, с независимым replay биномиального
цензурирования, восстановило **29 211 / 29 211** исторических проданных проектных
единиц. **False-positive units = 0; false-negative units = 0; несовпавших дней = 0**
на 147 936 исторических строках. Вход содержит 136 027 событий; 624 имеют проектный
суффикс. FP/FN здесь измерены в **единицах товара**, а не в количестве событий:
приватный ledger хранит дневные объёмы, а не полную разметку исходных документов.

Отдельный replay потока регулярного спроса подтвердил, что суффикс `1` раскрывает
**674 259 / 674 259** единиц регулярного крупного клиента; FP/FN по единицам и число
несовпавших дней равны нулю. Разграничение «сохранить регулярного клиента / удалить
проект» можно обойти через техническую нумерацию документов.

Это **утечка исторической классификации**, а не будущего спроса. Исторические
продажи сами по себе являются допустимым входом; недопустимая подсказка — код типа
покупки. `baseline.py:16` группирует события по `client_id` и не читает `event_id`.
При замене всех ID непрозрачными прогноз baseline совпал в **72/72 кейсах**.
Влияние этого дефекта на сохранённые численные результаты baseline не установлено;
дефект делает будущую сравнительную проверку внешних адаптеров уязвимой к обходу.

Для следующей версии: выдавать ID независимо от классификации и добавить
метаморфную проверку перестановки/переименования ID. Исправлять после просмотренного
final и называть те же seeds новым независимым holdout нельзя. В этом аудите
исправление намеренно не применено, чтобы сохранить воспроизводимость кандидата.

## GEN-02 — medium: пропуски в валидации публичного запроса

Точные места: `model/testbed/adapters.py:9` проверяет поля, но не тип/диапазон
`horizon_days`; `adapters.py:33` для акции проверяет лишь `announced_at`;
`adapters.py:36` не проверяет тип `complete`.

| Изменённый development-вход | Ожидалось | Фактически |
|---|---|---|
| `horizon_days=-1` | Отклонить | Принят |
| `horizon_days=True` | Отклонить boolean | Принят |
| `history[0].complete='false'` | Отклонить строку | Принят |
| `promotion.end_date < start_date` | Отклонить неверный интервал | Принят |
| `promotion.start_date='not-a-date'` | Отклонить неверную дату | Принят |

Это контрактный дефект для интеграции. Например, строка `'false'` является truthy
для проверки `baseline.py:39`, поэтому неполный период может восприниматься как
полный. Генератор текущих 72 кейсов создаёт корректные значения этих полей;
изменения в probe выполнялись только над копиями development-запросов.
Вывод об искажении уже сохранённых метрик из этого дефекта не следует.

## Что подтверждено отдельно от находок

- Все 72 кейса воспроизводятся точно; публичный request проходит текущую allowlist.
  В JSON нет полей `seed`, `scenario`, параметров генератора или скрытых рядов.
  `adapters.py:65` передаёт сериализованные наблюдения в отдельный процесс;
  `worker.py:20` вызывает выбранную внешнюю функцию.
- Будущие строки наблюдений и ещё не объявленная акция отклонены в отрицательных
  пробах; вложенные исторические даты и аналог не выходят за cutoff во всех кейсах.
  Объявленный план будущей акции — разрешённый наблюдаемый контекст.
- Суммы документов равны наблюдаемым дневным продажам на 147 936 строках.
  Повтор биномиального цензурирования из независимого потока согласуется со всеми
  строками; продажи не превосходят латентный спрос плюс проект; нулевая доступность
  даёт нулевые продажи. Суммарные остатки при доступности 0.25/0.5 находятся в пределах
  1.44 стандартного отклонения от аналитического ожидания.
- Shared regular stream действительно даёт одинаковую скрытую истину в stable,
  full/partial stockout и single/split project для всех шести seed/origin пар.
  Объём единого и разбитого проекта совпадает. Проекты хранятся отдельно от регулярной
  цели; регулярный крупный клиент входит в регулярный спрос.
- Проверено 15 отдельных Poisson-выборок по 10 000 наблюдений: seeds 101/202/303,
  средние 0, 0.1, 1, 20, 70. Среднее и дисперсия согласуются с распределением при
  заранее заданных широких sanity-порогах (6 SE и 15% относительного отклонения
  дисперсии). Это не доказательство всех свойств генератора.
- Для intermittent аналитическое ожидание `p*m` корректно; использованная
  контрольная дисперсия — `p*(2-p)*m²-p*m`. На 3 528 наблюдениях каждого SKU средние
  отличаются от ожиданий не более чем на 1.59 SE; частота положительного спроса
  7.51–8.48% при параметре 8%.
- Новый товар содержит 0 или 8 дней истории; будущий спрос положителен.
  Изменение только будущей приватной истины не меняет публичный JSON (72/72).
  Вызов baseline через штатный subprocess даёт тот же ответ, что прямой вызов.
- `verify_manifest` успешно выполнен перед пробами и после них.

## Ограничения оценки

`worker.py:10` импортирует доверенную функцию в общем filesystem. Это не OS sandbox;
злонамеренный адаптер может читать генератор/артефакты, и README уже прямо ограничивает
модель доверия (`README.md:68`). Аудит не утверждает защиту от такого адаптера.

В `generator.py:53` индекс SKU фиксирует масштабы 8/18/40/90 между всеми seeds.
Это облегчает запоминание синтетического каталога; обобщение на новые SKU отдельно
не доказано. Два origin являются независимыми симуляциями, а не rolling inventory.
Цензурирование экзогенно; расходование реального остатка и зависимость дефицита от
спроса не моделируются. Плановый множитель акции равен истинному; все сгенерированные
исторические строки `complete=True`, поэтому шум плана и неполнота импорта не
проверяются в основном прогнозном наборе.

Ожидание условно на приватном состоянии, включая заранее не известный модели
будущий shock (`generator.py:93`). Ошибка относительно него не равна ошибке
относительно математического ожидания, условного только на доступной модели
информации. Это также объясняет, почему ни успешные проверки инфраструктуры,
ни знание семейства распределений не гарантируют WAPE ≤10%.

Скрипт самостоятельно устанавливает cwd корня worktree относительно собственного
пути, отключает bytecode-запись и сохраняет только `generator.json` рядом с собой.
Новых `.py` нет; freeze не расширяется файлами probe. Он проверяет Python-версию
замороженного кандидата. Выход 0 означает, что пробы завершены без неожиданного
нарушения базовых инвариантов; **две подтверждённые находки остаются в `findings`**,
а не превращаются в «все проверки пройдены». Машинные доказательства —
[`generator.json`](generator.json), повторяемые пробы — [`generator.sh`](generator.sh).

Выполнена команда выше; затем независимый повтор из каталога самого скрипта.
Данные повторного запуска побайтово совпали. Любые численные WAPE берутся из
отдельного отчёта прогноза, а не из этих счётчиков проверок.
