# Проверяемое ядро прогноза и закупочных расчётов

Исправленный кандидат `testbed-v3.0-corrections`. Область — `model/testbed/`: офлайн
Python, без UI, HTTP-сервиса и автоматической отправки заказов. Это локальный стенд
и референсный калькулятор, не подтверждённый production-модуль.

Результат проверки исходного PDF и всех 12 Excel-выгрузок:
[отчёт исправлений](audits/corrections/REPORT.md). Источники побайтно совпадают с
ранее выданными входами. Их хеши, схемы и агрегированное покрытие сохранены в
[инвентаризации](audits/corrections/source-inventory.json), без исходных записей.

## Запуск

Из корня worktree, Python **3.14.4** для точного воспроизведения. Внешние пакеты
не нужны. `corrected-freeze.json` проверяет код, протокол, тесты, фикстуры,
адаптеры и версию Python.

```bash
bash model/testbed/audits/corrections/run.sh
```

Команда запускает unit tests, контроли MH1–MH5, development и повторное измерение
на ранее просмотренных final seeds, регрессионные проверки и независимый
Decimal-пересчёт WAPE/MAE/bias. Результаты: `reports/corrected-development/`,
`reports/corrected-final/`, `audits/corrections/`. Высокий WAPE не выдаётся за
успешную приёмку: runner отдельно проверяет код `--require-target`.

Отдельные команды:

```bash
python3 -m unittest discover -s model/testbed/tests -v
python3 -m model.testbed.requirement_checks --output model/testbed/audits/corrections/requirements.json
python3 -m model.testbed.run evaluate --split development --output model/testbed/reports/corrected-development
python3 -m model.testbed.run evaluate --split final --require-target --output model/testbed/reports/corrected-final
python3 -m model.testbed.source_inventory --folder '/путь/к/папка' --output model/testbed/audits/corrections/source-inventory.json
```

Код 2 — ошибка прогноза, арифметики, бизнес-проверки или парной MH4. Код 3 —
порог WAPE не достигнут при `--require-target`. Код 0 аудита означает воспроизведение
проверок и доказательств, а не точность прогноза 100%.

## Исправления

- Непрозрачные ID событий и перемешанный порядок документов убирают прямую
  подсказку об историческом классе покупки.
- Строгая проверка ISO-дат, горизонта 1..366, boolean `complete`, порядка истории,
  известности и положительного коэффициента акций.
- Проверка конечности дней, горизонтов и общей ошибки. При отказе строки и
  доступные цели сохраняются, метрики становятся `null`. Разные единицы не смешиваются.
- Общая схема и инварианты ответа проверяются до subset-сравнения с фикстурой.
- Количества, деньги и вероятности считаются Decimal до преобразования в JSON;
  q=1 при принятой погрешности массы больше не обнуляет целевой запас.
- Траектория с предложенным заказом на ETA выявляет остаточный дефицит после ETA,
  отдельно от раннего дефицита. Источник экономических параметров сохраняется.
- Строка заказа содержит численное объяснение и `urgency`: data_required,
  review_required, expedite, routine или no_order.

12 прежних подтверждённых категорий покрыты регрессионными проверками. BIZ-07
разрешён как контракт: при неизвестных MOQ/кратности количество — предварительная
потребность `provisional_base_need`, а не допустимая партия. Известные ограничения
выведены отдельно, `needs_review` блокирует утверждение. MOQ опционален для прогноза.

## Прогноз и история

По умолчанию используется `model.testbed.seasonal:forecast`. Для каждого товара
выбирается среднее за 56/168 дней либо регрессия логарифма недельного среднего с
линейным трендом и двумя годовыми гармониками, с калибровкой дней недели.
Решение принимается по трём внутренним 28-дневным окнам до текущего cutoff.
Каждый fit заново обрезает историю, события и объявления акций на свою дату.
Для сезонной регрессии нужен минимум год истории. При редком спросе используется
среднее. Набор методов и правила фиксированы до повторного final.

Клиентские покупки объединяются в семидневное окно; повторяющийся клиент не
удаляется как проектный. При нулевой типичной дневной продаже редкая положительная
покупка больше не объявляется выбросом автоматически. Это эвристика для синтетики;
реальные клиентские метки в представленных выгрузках отсутствуют.

Известная доступность используется как экспозиция, акции нормализуются; новый товар
может использовать предоставленный прошлый аналог. Неизвестные сведения не
заменяются выдуманными значениями. Старое среднее доступно явно через
`--adapter model.testbed.baseline:forecast`.

## Требования кейса

| Требование | Исполняемое доказательство в requirement_checks.py |
|---|---|
| MH1 | Влияние прогноза, запаса, пути, категории и прироста на количество |
| MH2 | Контроли сезонности и устойчивого роста; сравнение с плоским средним |
| MH3 | Известный stockout повышает прогноз против сырых продаж |
| MH4 | Одиночный и разбитый проект: устойчивость прогноза и заказа |
| MH5 | Прогноз → калькулятор → два поставщика, численное объяснение и срочность |

`audits/corrections/example-orders.csv` помечен `synthetic_reference` и требует
ручного утверждения. Поля: mode, supplier_id, sku, quantity, unit, status, urgency,
reason, requires_manual_approval. Это табличный контракт; совместимость с конкретным
импортом 1С не подтверждена. В интеграционном контроле используется точечное
детерминированное распределение, не калиброванный интервал неопределённости.

`approval_blocked=false` означает отсутствие проверенных блокирующих условий,
не означает «утверждено». Отправки заказа и действий от имени менеджера нет.

## Метрики и ограничения

WAPE = Σ|P−Y|/ΣY, MAE = Σ|P−Y|/N, bias = Σ(P−Y)/ΣY; P и Y — суммы за 28 дней
на SKU. Дневные ошибки приведены отдельно, с модулем до суммирования дней.
При нулевом знаменателе WAPE/bias неопределены, строки остаются. Группы: сценарий,
seed, cutoff, единица и SKU. MAE горизонта измеряется в единицах на SKU за 28 дней.

Цель стенда — скрытый реализованный **синтетический регулярный спрос**. Реальные
наблюдаемые продажи из forecast_v2 — другая оценка. Счётчики тестов, синтетический
WAPE и ошибка реального прогноза не объединяются. Порог ≤10% остаётся неподтверждённым.

В XLSX нет ID клиентов и точных stockout-интервалов. Месячные остатки не задают
дневную доступность, документы не заменяют клиентов. SE содержит снимок остатков,
резервов и категорий, но этот снимок недоступен историческим origin. ETA имеющегося
заказа не равен сроку нового заказа. Полные сезонные коэффициенты не допускаются
в прошлый прогноз. SE «Кратность» и IEK «Мин. разр. к отгр.» имеют разные значения.
Месячные продажи не добавляются к детализации за те же периоды и не превращаются
в якобы наблюдаемые дни. Отрицательные строки требуют различать положительные
отгрузки, возвраты/корректировки и нетто-движение.

Четыре синтетических SKU и точная экспозиция не воспроизводят весь ассортимент.
Subprocess — граница JSON для доверенного кода, не OS sandbox. Реальная приёмка,
экономика и 1С требуют дополнительных сведений и проверки.

## История и заморозка

`freeze.json`, `reports/development/`, `reports/final/`, `RESULTS.md` и два прошлых
аудита сохранены как история v2. Их воспроизведение требует checkout

ретроспективным сравнением даже после нового freeze.
