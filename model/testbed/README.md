# Offline testbed: прогноз, закупочный расчёт и проверка реальных входов

Работа ограничена `model/testbed/`. Это проверяемый локальный reference и набор
экспериментов; готовый сервис, автоматическая закупка и WAPE ≤10% не заявляются.
Точность прогноза измеряется отдельно от количества пройденных проверок.

Текущие исправления и доказательства: [audits/full/REPORT.md](audits/full/REPORT.md).
Предыдущая версия: [audits/corrections/REPORT.md](audits/corrections/REPORT.md).
Исторические отчёты, fixtures и старые freeze сохранены. Для их воспроизведения
нужен исходный коммит; новый код намеренно не проходит старый freeze.

## Воспроизведение синтетического эксперимента

Python **3.14.4**, стандартная библиотека, из корня worktree:

```bash
bash model/testbed/audits/full/run.sh
```

Команда проверяет `full-freeze.json`, выполняет unit tests, 11 функциональных
must-have контролей, оба split и независимый Decimal-пересчёт CSV/JSON.
`--require-target` возвращает **3**, если WAPE >10%; это сохраняется в доказательствах,
а не превращается в PASS точности. Ошибки выполнения или пропуски прогнозов дают
код **2** и не позволяют считать метрику только по успешным строкам.

```bash
python3 -m model.testbed.run evaluate --split development --output model/testbed/reports/full-development
python3 -m model.testbed.run evaluate --split final --require-target --output model/testbed/reports/full-final
```

Final seeds ранее просматривались. Текущий результат — ретроспективное сравнение
зафиксированного кандидата, **не новый независимый holdout**. Генератор не менялся
в этой итерации. Латентные цели проверяются на точное совпадение с прошлой версией.

## Модель и контракт

`seasonal:forecast` выбирает mean56, mean168 или сезонную регрессию по трём
внутренним 28-дневным окнам, каждый раз обрезая историю и объявления акций на
соответствующую дату. Внутренний target — наблюдаемые продажи; скрытые регулярные
цели для выбора недоступны. Сезонная регрессия использует тренд, две годовые
гармоники и день недели. Поправки на доступность допустимы только при явно
известной экспозиции. В реальных XLSX такой информации нет.

Нет свежей наблюдаемой экспозиции или явно переданного аналога за 168 дней —
явная ошибка недостатка истории. Отсутствие данных не выдаётся за нулевой спрос.
Клиентская эвристика учитывает известные акции и сохраняет повторные покупки с
интервалом хотя бы 7 дней. Это эвристика, не универсальный классификатор проектов;
номера накладных из реальных выгрузок не превращаются в клиентов.

`business:reference_calculate` использует Decimal, поддерживает отрицательный net
stock, явные policy/economics, MOQ и кратность с отдельной семантикой, календарь
поступлений и дефицита. Неизвестные обязательные данные дают `needs_data` и
`quantity=null`. Неизвестное условие партии даёт только `provisional_base_need`,
требует проверки и блокирует утверждение. Требование ручного утверждения сохраняется.

Checker сравнивает внешнее вычисление с явно заданным reference-контрактом.
Его соответствие не доказывает оптимальность политики; независимые числовые
ожидания находятся в tests. Исходные 54 бизнес-фикстуры сохранены.

## Реальные данные и сохранённые веса

Реальная модель находится в отдельной ветке `codex/forecast-v2`, опубликованный
совместимый коммит `2282c2042dfb38a8aca17fb97219a55de28165ee`. Её веса здесь не
переобучаются и не дублируются. Используется отдельное Python 3.12 окружение с
`model/forecast_v2/requirements.txt`; `replay_real` проверяет алгоритм, веса,
выбор метода и исходные файлы. Внешний checkout не должен иметь tracked changes.

```bash
bash model/testbed/audits/full/run-real.sh \
  /path/to/forecast-v2 /path/to/python312 \
  /path/to/inputs /path/to/forecast-v2-private /path/to/new-private
```

Нужны исходные два каталога XLSX и прежние приватные prediction CSV. Команда:

1. Заново восстанавливает из XLSX положительные наблюдаемые отгрузки на даты
   04.05, 01.06, 29.06, 27.07 и 24.08.2026, горизонт 28 дней. Проверяет universe,
   нулевые/новые товары, past-only группы и ABC, затем WAPE/MAE/bias по единицам.
2. Запускает **сохранённые** веса и сверяет текущий прогноз с прежним выводом.
3. Создаёт приватные `procurement-review.json` / `.csv`: прогноз, найденные
   строки MOQ/кратности и SE stock snapshot, неизвестные и блокировки по товарам.
   Это пакет для проверки исходных данных, **не готовый список заказов**.

`real-metrics.json` проверяет арифметику сохранённых prediction CSV и их цели,
но не переобучает исторические модели. `real-replay.json` доказывает новый запуск
сохранённых весов, но не измеряет будущую точность. Эти утверждения разделены.

Положительные invoice sales — исходная цель forecast_v2, не нетто с возвратами.
Месячные 2024 используются внешней моделью только как отдельные агрегатные признаки;
к дневной цели они не прибавляются. Нынешние stock/category/seasonality snapshots
не подаются в исторический прогноз. Строки и идентификаторы партнёров, caches и
прогнозы остаются вне Git; в репозиторий попадают только агрегаты и SHA-256.

Неизвестны lead time нового заказа, политика сервиса/издержек, согласованный
актуальный складской срез, закупочные цены и полноценная история stockout/клиентов.
Из одного point forecast не создаётся фиктивное распределение спроса. Поэтому
реальные количества заказа остаются заблокированными. Совместимость импорта 1С
и production readiness не заявляются.
