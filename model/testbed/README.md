# Воспроизводимая среда закупок v2

Программная синтетическая среда без UI, HTTP и внешних зависимостей. Все файлы
изменения находятся в `model/testbed/`. Исходные требования:
[`requirements-matrix.md`](../../docs/requirements-matrix.md) и
[`decision-rules.md`](../../docs/decision-rules.md).

Это среда оценки и интеграционные примеры, а не обученная модель и не готовый
закупочный движок. Встроенный baseline нужен для воспроизводимого первого запуска.
Расчётная функция `reference_calculate` иллюстрирует контракт; её успешные проверки
не доказывают корректность ещё не подключённого производственного модуля.

## Запуск

Из корня этого worktree, Python 3.10+ (сохранённый финальный прогон: Python 3.14.4).
Установка пакетов не нужна.

```sh
python3 -m unittest discover -s model/testbed/tests -v
python3 -m model.testbed.run evaluate --split development --output model/testbed/reports/development
python3 -m model.testbed.run evaluate --split final --output model/testbed/reports/final-replay
```

Последняя команда проверяет сохранённый `freeze.json`, включая версию Python.
Для точного воспроизведения используйте указанную в нём версию. Уже просмотренные
final seeds нельзя снова называть независимым holdout для изменённой модели.

До **первого** финального прогона новой версии кандидата:

```sh
python3 -m model.testbed.run freeze --manifest model/testbed/candidate-freeze.json
python3 -m model.testbed.run evaluate --split final --manifest model/testbed/candidate-freeze.json --output model/testbed/reports/candidate-final
```

`freeze` отказывается перезаписывать существующий manifest. В нём SHA-256 всех
Python-файлов среды, protocol, фикстур, модулей адаптеров, выбранных весов/конфигов,
версия Python и исходный Git commit. Final отказывается работать при расхождении.
Отчёты и README не входят в хеш кода, чтобы можно было документировать результат.
Это аудируемый локальный протокол, а не защита от преднамеренного редактирования
manifest. Удалять freeze и подбирать новую версию по тем же final результатам нельзя.

Файлы результата: `report.json` (включая каждый SKU, срез, seed, сценарий и проверку),
`rows.csv` (построчные прогнозы и цели), `report.md` (таблицы всех сценариев × seeds).
Код завершения 2 — ошибка адаптера/бизнес-проверки/парной MH4, 3 — недостигнутая цель при
`--require-target`; без этого флага высокий WAPE остаётся результатом измерения.

## Разделение данных

1. **Наблюдения модели**: продажи по дням, доля доступности 0..1, признак полноты дня,
   исходные документы с псевдонимами клиентов, товар/категория/единица/поставщик,
   дата запуска, прошлый ряд аналога для нового товара и заранее объявленные акции.
   ID клиентов меняются между seeds; постоянной метки «проектный клиент» нет.
2. **Истина оценщика**: реализованный регулярный спрос и его математическое ожидание,
   в том числе потерянный при отсутствии товара. Будущие значения доступны только
   оценщику после возврата прогноза.
3. **Разовые проектные покупки**: отдельный ряд. Историческая реализованная часть
   входит в наблюдаемые документы без метки «проект», а будущая не попадает в цель
   регулярного прогноза. История не удаляется ради очистки.

`EvaluationCase` остаётся в процессе оценщика. Адаптер запускается отдельным
процессом, получает JSON только пункта 1 через stdin. В аргументах нет seed,
сценария, параметров генератора или путей к истине. Allowlist проверяет поля на
каждом уровне; будущие наблюдения, ещё не объявленные акции и дубликаты ID
отклоняются. Изменение входа адаптером не меняет данные оценщика. Ошибка/timeout,
NaN, отрицательный прогноз, пропуск SKU или неверный горизонт дают ошибочные строки
в отчёте; WAPE полной группы становится `null`, а не считается по удобному остатку.

Это граница данных для доверенной локальной функции, **не OS sandbox**. Внешнему
недоверенному коду нельзя предоставлять общий filesystem с генератором и отчётами.
Модель должна обучаться только на данных до cutoff; среда не может доказать дату
обучения произвольных внешних весов. Их происхождение указывает владелец адаптера.

Экспорт примера (разрешены только development seeds):

```sh
python3 -m model.testbed.run export-development --scenario split_project --seed 101 --output model/testbed/sample
```

`model-input.json` передаётся модели; `evaluator-only/regular-truth.json` и
`evaluator-only/project-purchases.json` предназначены только для оценщика.

## Сценарии и генератор

Протокол зафиксирован в [`protocol.json`](protocol.json): development seeds
**101, 202, 303**; final seeds **909, 1337, 2027, 4099**. Два cutoff:
2025-07-01 и 2026-04-01; 560 дней истории, горизонт 28 дней, 4 SKU на сценарий.
Итого 288 строк development и 384 final. Срезы — независимые воспроизводимые
ансамбли, а не непрерывная симуляция движения запасов.

| Сценарий | Конструкция |
|---|---|
| `stable` | Poisson, недельный профиль, разные масштабы SKU |
| `seasonal_growth` | Годовая сезонность с разной фазой и устойчивый экспоненциальный рост |
| `intermittent` | Bernoulli-событие × геометрический размер покупки; нулевые горизонты сохраняются |
| `new_product` | Два SKU без истории, два с 8 днями истории; шумный прошлый аналог категории |
| `full_stockout` | Полная недоступность внутри 42-дневного блока истории |
| `partial_stockout` | Доступность 0, 25%, 50%, 100%; независимое биномиальное цензурирование |
| `single_project` | Крупная разовая покупка, отдельные исторический и будущий проекты |
| `split_project` | Тот же общий объём одного клиента разбит на 15 документов за 3 дня |
| `recurring_client` | Еженедельные крупные покупки одного клиента входят в регулярный спрос |
| `known_promotion` | Прошлая и будущая акции с заранее известным плановым коэффициентом |
| `demand_shock` | Скачок ×3.5 на 14 будущих дней без наблюдаемого предвестника |
| `combined` | Сезонность, рост, частичная доступность, разбитый проект, акция, неожиданный скачок |

Генератор использует стандартный `random.Random` с SHA-256 производных потоков.
Poisson генерируется точно суммой небольших независимых Poisson; нормальной
аппроксимации нет. Математическое ожидание compound intermittent вычисляется
аналитически, а не по реализованной будущей выборке. Для regular/project/availability
разные потоки; stable, stockout и проекты имеют одинаковый латентный регулярный
путь для парных сравнений. Все SKU прогноза в `шт`; WAPE разных физических единиц
не смешивается. Метры и упаковки проверяются в закупочных фикстурах.

Ожидание условно на полном состоянии симулятора, включая неизвестный будущий шок.
Поэтому даже отсутствие случайного Poisson-шума не делает его полностью
предсказуемым по доступным на cutoff данным. Цель **WAPE ≤10%** не гарантируется.

## Метрики

Основная метрика по полному 28-дневному горизонту:

`WAPE_realized = Σ |Σ forecast_daily − Σ latent_regular_daily| / Σ latent_regular_daily`.

Отдельно `WAPE_expectation` с аналитическим ожиданием вместо реализованного спроса.
Публикуются absolute error, bias, количество нулевых целей и дневные WAPE, где
абсолютная ошибка берётся **до** суммирования дней. Основная горизонтная метрика
допускает компенсацию дневных ошибок внутри SKU — это явно другое измерение.
Агрегирование использует суммы ошибок/объёмов, а не среднее процентов. При нулевом
знаменателе WAPE `null`; абсолютная ошибка и строка остаются. Проектный объём виден
отдельно и не увеличивает знаменатель регулярного спроса.

Результаты есть по каждому seed, сценарию, паре scenario/seed, cutoff и SKU.
Трудные сценарии не исключаются. **90% пройденных тестов не означает 90% качества
прогноза**; доля прохождения бизнес-правил — отдельная величина.

## Подключение прогноза

```python
def forecast(request: dict) -> dict[str, list[float]]:
    # request: schema_version, as_of, horizon_days, items
    # Return exactly every requested SKU and horizon_days finite nonnegative numbers.
    return {item["sku"]: [1.0] * request["horizon_days"] for item in request["items"]}
```

```sh
python3 -m model.testbed.run evaluate --split development --adapter my_package.adapter:forecast --output model/testbed/reports/external-dev
python3 -m model.testbed.run freeze --adapter my_package.adapter:forecast --artifact /path/to/weights.bin --artifact /path/to/config.json --manifest model/testbed/external-freeze.json
```

Модуль должен быть доступен в Python path; рабочий каталог — корень репозитория.
Владелец внешнего адаптера фиксирует все его транзитивные зависимости/веса через
`--artifact` (по одному файлу) и отдельное окружение. Автоматически хешируется
файл модуля функции, а не произвольный внешний пакет целиком. stdout модели
перенаправляется в stderr, transport — JSON. Timeout по умолчанию 30 секунд на вызов.

Встроенный baseline: средний спрос за 56 дней с экспозицией доступности; клиентские
события объединяются в 7-дневном окне; крупная группа >8 дневных медиан исключается
лишь при отсутствии повторяемости ≥3 недель. Плановые акции нормализуются, новый
товар смешивается с аналогом. Гиперпараметры заданы до final. Baseline не моделирует
годовую сезонность/тренд, не обещает идеальной очистки и не обучает CatBoost из `model/`.

## Независимые закупочные проверки

[`fixtures/business_cases.json`](fixtures/business_cases.json) содержит **54** полных
входа и вручную заданные ожидаемые результаты. Они не вычисляются вызываемой
расчётной функцией. Checker сравнивает поля с числовым допуском 1e-8, проверяет
rule IDs и наличие объяснения. Он отклоняет `null`, bool/NaN вместо чисел.

| Требования | Контроль |
|---|---|
| MH1, SUPPLY-01 | Запас, резерв, готовый net free_stock, только неучтённые обязательства, даты |
| SUPPLY-02 | Своевременное/позднее/отменённое поступление, граница горизонта, ранний дефицит |
| SUPPLY-03/04 | MOQ, кратность, нулевая потребность, неизвестные ограничения, м/шт/упаковка |
| MH1, DEMAND-04 | Категория, внешний прирост на весь/часть периода, уже включённый коэффициент |
| POLICY-01/02 | Индивидуальные underage/overage, минимум категории, отсутствие экономики, редкий дорогой проект |
| BUDGET-01/02, MH5 | Неизвестная цена, превышение/равенство бюджета, сумма и группы двух поставщиков |
| DATA-01 | Нет/устарел запас, нет резерва/срока/политики/прогноза, горизонт и единицы |

Контракт расчётного адаптера: `calculate(request: dict) -> dict`, формы входа и
ожидаемого выхода представлены полностью в фикстурах. Это локальный тестовый
контракт, не заявление о точном соответствии HTTP OpenAPI. Для реального модуля
нужна функция преобразования его типов к этому контракту:

```sh
python3 -m model.testbed.run evaluate --split development --calculator my_package.adapter:calculate --output model/testbed/reports/calculator-dev
python3 -m model.testbed.run check-business --calculator my_package.adapter:calculate --output model/testbed/reports/business.json
```

Ожидаемые ответы допускают дополнительные поля. Расчётный адаптер тоже запускается
в отдельном процессе. По умолчанию отчёт явно помечает статус `reference_only`.
Сначала проверяются данные, потом обязательства/физические ограничения, экономика,
бюджет. `free_stock` считается уже очищенным от резерва. Ведомость содержит
`already_accounted_quantity`, включающую уже учтённую или зарезервированную часть.
Поступления в начале дня, спрос в конце; день 1 — следующий после as_of. Неучтённые
просроченные обязательства приходятся на день 1. Ранее просроченный inbound без
подтверждённой новой ETA не считается своевременным поступлением.

В примерах `horizon_distribution` — явное дискретное распределение спроса **за весь
горизонт**; его квантиль выбирается по underage/(underage+overage) с минимумом
категории. Дневные квантили не суммируются. Для внешнего прироста демонстрационная
функция пропорционально масштабирует горизонтное распределение по изменению среднего;
это допущение примеров, а не универсальный метод калибровки. Ранний дефицит ищется
по дневному среднему; предлагаемый обычный заказ не стирает разрыв до своего ETA.
Округление Decimal; конверсия упаковки должна быть задана явно.

Парные MH4 дополнительно сравнивают baseline до/после единичного и разбитого проекта
на каждом seed/cutoff/SKU: прогноз ≤10%, количество ≤max(10%, одна единица/партия).
Здесь количество — прозрачная проекция `ceil(forecast)` при запасе/пути 0,
MOQ=кратность=1; это не проверка всего внешнего расчётного модуля. В unit tests также
проверено, что повторяющийся крупный клиент сохраняется, а stockout-компенсация
повышает прогноз относительно сырых продаж.

## Ограничения и результаты

Зафиксированный baseline: final WAPE **25.85%** по реализованному скрытому
регулярному спросу и **24.69%** по математическому ожиданию. Цель ≤10% не достигнута.
384 строки, ошибок адаптера 0; 54/54 примеров на reference calculator и 64/64
парных MH4. Это разные измерения. Подробный разбор — [`RESULTS.md`](RESULTS.md).

Итоговые результаты сохраняются в [`reports/final/report.md`](reports/final/report.md),
development — в [`reports/development/report.md`](reports/development/report.md).
Они измеряют синтетику, а не качество на данных партнёра. Встроенный алгоритм слаб
при прерывистом спросе, меняющейся сезонности/росте и неанонсированных скачках;
история доступности считается достоверной, а коэффициент акции — заданным планом.
Ошибки этих источников, замещение SKU, возвраты, зависимость дефицита от спроса,
стоимость доставки и оптимизация общего бюджета пока не моделируются.
Approval/revision, экспорт в 1С и AI fallback лежат вне этой программной среды.
Автоматического утверждения или отправки заказа нет.

подтвердил опубликованные WAPE и выявил открытые дефекты: `event_id` раскрывает

партии/бюджета и неотражённый разрыв поставок после ETA обычного заказа.

повторения сохранены в audit-папке. Успешные исходные тесты не означают завершённую
приёмку среды или точность прогноза.
