# Офлайн-математика заказа

`core.py` рассчитывает отдельный SKU/склад, группирует результат по поставщикам
и проверяет возможность ручного утверждения. В модуле нет HTTP, интерфейса,
отправки заказов, обучения модели или вызова LLM. Прогноз передаётся извне.

```python
from datetime import date
from model.decision.core import (
    EconomicProfile, InventorySnapshot, RecommendationInput,
    SupplierConstraint, recommend,
)

as_of = date(2026, 9, 22)
result = recommend(RecommendationInput(
    sku="001", warehouse_id="ALM", supplier_id="SE", unit="шт",
    unit_quantum=1, as_of=as_of, forecast_as_of=as_of,
    forecast_id="explicit-demo-scenarios-v1", data_version="demo-v1",
    scenarios=((2, 4, 3, 1), (3, 5, 4, 2)),
    inventory=InventorySnapshot(as_of, on_hand=4, reserved=1, source="demo"),
    lead_time_days=2, review_period_days=2,
    constraints=SupplierConstraint("шт", min_order_qty=2, order_multiple=2,
                                   source="supplier-profile-v1"),
    economics=EconomicProfile(9, 1, 4, "KZT", "explicit scenario, not partner prices"),
))
print(result.quantity, result.reason)
```

Запуск проверок из корня репозитория, Python 3.10+; внешние библиотеки не нужны:

```sh
python -m unittest model.decision.test_core -v
```

## Даты, единицы и неизвестные значения

- `as_of` — конец последнего наблюдённого дня. Колонки сценария соответствуют
  датам `as_of+1` … `as_of+H`. `H=lead_time_days+review_period_days`.
  Новый заказ приходит **в начале** даты `as_of+lead_time_days`, до спроса этого дня.
  При `lead=0` он доступен сразу. Это календарные дни, не рабочий календарь.
- `scenarios` — совместные дневные траектории одинакового горизонта с равным весом.
  Внутридневные события агрегированы. Модуль не складывает дневные квантили.
  Калибровку/реалистичность сценариев подтверждает отдельная проверка прогноза;
  одна детерминированная траектория не доказывает вероятностную гарантию.
- Все количества передаются в складской `unit`. `unit_quantum` задаётся явно:
  например, 1 штука или 0.1 кг. Остатки, поступления и материальные аллокации
  должны лежать на этой физической решётке. Сам прогноз может быть дробным.
- MOQ и кратность задаются в `constraints.order_unit`. Для другой единицы нужен
  явный `inventory_units_per_order_unit`; преобразованная кратность должна быть
  совместима с `unit_quantum`. Одинаковые единицы означают точную конвертацию 1.
  Сравнения решётки, ceil/floor, конвертация и бюджет используют десятичную арифметику.
- Известная кратность поставщика и физическая единица — разные ограничения.
  При неизвестных MOQ/кратности/конвертации: `needs_review`, `quantity=None`,
  `provisional_quantity` с подтверждёнными ограничениями и физическим округлением.
  Неизвестное условие остаётся `None` в диагностике и не заменяется скрытым 0 или 1.
- Отсутствующие актуальные остатки, срок, горизонт, физическая единица округления,
  прогноз или экономика/явная политика: `needs_data`, оба количества `None`.
  Допустимый возраст снимка/прогноза по умолчанию 0 дней; расширение задаётся явно.
  Будущие даты снимка/прогноза, отрицательные/NaN/бесконечные числа, дубли ID,
  несовместимые единицы и противоречивые количества дают `ValueError`.
  Просроченный открытый inbound требует обновлённой ETA; его нельзя считать
  полученным и повторно добавить к текущему запасу.

## Запас, поступления, прирост, обязательства

При наличии `free_stock` резерв повторно не вычитается. Если представлены все три
поля, проверяется `free_stock=on_hand-reserved`. Без `free_stock` нужны оба поля
`on_hand` и `reserved`; пропуск резерва не означает ноль.

Поступления учитываются по датам. Поздний inbound не компенсирует уже упущенную
продажу; ранний дефицит до нового заказа сохраняется в объяснении и диагностике.
События за пределами горизонта остаются в происхождении результата с
`in_horizon=False` и не изменяют запас внутри горизонта.

Внешний прирост имеет ID, источник и включительный диапазон дат. Он умножает
только регулярную часть на `1+rate` в этом диапазоне. ID из `included_growth_ids`
помечается как уже включённый в прогноз и повторно не применяется. Разные
переданные корректировки перемножаются; вызывающая сторона отвечает за то,
что разные ID не представляют один и тот же бизнес-план.

Материальная строка задаёт количество, дату, источник и **непересекающиеся** части
`included_in_forecast` и `already_reserved`, с `accounting_source` для аллокаций.
Количество, увеличивающее совокупный спрос, равно
`quantity-included_in_forecast-already_reserved`. Чтобы сохранить жёсткий статус
уже включённого обязательства, на его дату из каждой траектории выделяется
`included_in_forecast`, а материальный поток получает `quantity-already_reserved`.
Повторного добавления нет. Если заявленное включение больше траектории на эту дату,
вход противоречив и отклоняется. Фиксированное обязательство не увеличивается
внешним коэффициентом роста регулярного спроса.

В каждый день поступления доступны до потребления; затем обслуживаются жёсткие
незарезервированные обязательства, затем регулярный спрос и мягкие обязательства.
Резервы считаются выделенными отдельно и удалены из свободного запаса один раз.
Рекомендация покрывает жёсткие обязательства после прихода нового заказа **во всех
переданных сценариях**. Сценарий с большим регулярным спросом до даты обязательства
может потребовать большего заказа: постоянного упреждающего резервирования будущего
материала из свободного запаса этот модуль не выполняет. Если это нужно бизнесу,
такой резерв должен быть явно отражён в исходных данных.

Жёсткая потребность до даты обычной поставки не переносится молча в будущее:
она даёт `hard_material_shortage_before_arrival`, `needs_review` и `expedite`.
Требуется отдельное решение об ускорении/переносе обязательства. Модуль моделирует
упущенный спрос (`lost sales`); очередь backorder и обещание исполнить просрочку
позднее должны быть отдельным входом/расчётом.

## Экономика и точная дискретная партия

Для каждого сценария симуляция без нового заказа даёт:

- `A`: недопроданный спрос до даты прихода нового заказа;
- `R`: недопроданный спрос с этой даты до конца горизонта;
- `E0`: конечный запас без нового заказа.

При неизменных датах остальных поступлений, отсутствии порчи и одной новой партии:

```text
lost(Q) = A + max(R - Q, 0)
ending(Q) = E0 + max(Q - R, 0)
loss(Q) = underage_cost * E[lost(Q)] + overage_cost * E[ending(Q)]
```

Цены потерь относятся к одной валюте и одному горизонту. `underage_cost` — обоснованная
потеря вклада/доступности. `overage_cost` — капитал, хранение и обесценение с учётом
остаточной ценности. Полная закупочная цена не добавляется к overage автоматически.
`unit_cost` используется отдельно для бюджета, не подменяет стоимость избытка.

Без дополнительных ограничений критическая доля равна `underage/(underage+overage)`.
Для MOQ/кратности выбирается минимум ожидаемых потерь среди **0 либо допустимых
партий**. Достаточно соседних точек физической/поставщицкой решётки около изломов
`R`, MOQ и нижних границ. Произвольного `qmax` и полного перебора больших количеств
в рабочем расчёте нет. Нельзя всегда округлять непрерывный оптимум вверх до MOQ:
нулевой заказ иногда дешевле. При одинаковых потерях выбирается меньшее количество.

Явная политика SKU и политика категории задают минимальную долю сценариев без
дефицита **после прихода заказа**. Применяется больший из переданных минимумов;
категория может поднять нижнюю границу экономического решения. Это эмпирическая
доля сценариев, не доказанный в реальном мире service level и не fill rate.
Без экономики допускается такая явная политика; стоимость потерь остаётся `None`.
Нерасшифрованная категория не получает придуманного значения: `needs_review`.

## Группировка и утверждение

`group_by_supplier` сохраняет объяснение каждой строки, включая `needs_data`,
и отклоняет дубли поставщик/склад/SKU.

`check_approval` — чистая проверка, не сохранение или отправка заказа. Она требует
имя подтвердившего сотрудника и совпадение revision, повторно проверяет физическую
единицу, MOQ/кратность, материальный и service minimum. `needs_review` требует
причину по ключу `(supplier_id, warehouse_id, sku)`. Комментарий не отменяет
неизвестное количество, отсутствие данных или жёсткие ограничения.

При заданном бюджете положительная выбранная партия должна иметь цену за складскую
единицу и совпадающую валюту; неизвестная цена не равна нулю. Превышение блокирует
утверждение. Глобального оптимизатора распределения бюджета нет. Без бюджета
отсутствие цены допустимо, суммарная стоимость остаётся `None`.

Результаты и их диагностика здесь считаются доверенными внутренними объектами.
Это не граница аутентификации и не защита от подделки входного JSON. Платформа должна
хранить исходный расчёт, повторно вычислять диагностику после редактирования,
атомарно сверять revision и создавать неизменяемый утверждённый снимок.

## Что проверено

Unit-проверки покрывают экономику, MOQ против простого округления, категории,
траектории, даты inbound, ранний дефицит, аллокации и приоритет материала, рост,
пропуски, единицы, дробные партии/бюджет, дубли, устаревшие данные и утверждение.
400 воспроизводимых случайных задач сравниваются с независимым дневным симулятором
и исчерпывающим перебором допустимых партий. Ещё 150 задач проверяют монотонность
по запасу, своевременному inbound, стоимости потерь и политике доступности.

Это функциональная проверка математического модуля. Её доля прохождения не является
точностью ML-прогноза. Здесь не проверяются качество исходной доступности, полнота
клиентских данных, прогнозные WAPE/MAE, гарантии сроков поставщика и реальные цены.

Ограничения: один новый заказ/SKU, детерминированный lead, равные веса сценариев,
отсутствие порчи, ограничений вместимости, совместных скидок и цепочки замен товаров.
При изменении этих предпосылок формула и оптимизатор потребуют расширения и новых тестов.
