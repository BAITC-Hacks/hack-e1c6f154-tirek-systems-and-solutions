# Tirek backend

FastAPI + SQLite. Аккаунты, демо-провайдер, прогноз и расчёт закупки SE/IEK через сохранённые веса v2. Они используют общий HTTP-контракт.

## Запуск из корня репозитория

```powershell
py -3.12 -m venv .venv-ml
.\.venv-ml\Scripts\python.exe -m pip install -r backend/requirements-ml.txt
.\.venv-ml\Scripts\python.exe -m uvicorn backend.app.main:app --host 127.0.0.1 --port 8000
```

Полный стек проверен на Python 3.12 / Windows. Python 3.14 со старыми зависимостями платформы не является окружением модели. API: http://127.0.0.1:8000/docs. База по умолчанию `data/tirek.sqlite3`. Для другого диска перед запуском задайте `$env:DATA_DIR = 'D:\tirek-data'`. Переменные из `.env.example` — образец; задайте их в окружении либо передайте uvicorn `--env-file backend/.env`.

Если Python 3.12 ещё не установлен, можно установить отдельное окружение через uv:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install uv
.\.venv\Scripts\uv.exe venv --python 3.12 .venv-ml
.\.venv\Scripts\uv.exe pip install --python .venv-ml\Scripts\python.exe -r backend/requirements-ml.txt
.\scripts\dev.ps1
```

`dev.ps1` предпочитает `.venv-ml`, иначе использует `.venv`; другой интерпретатор
задаётся через `-PythonPath`. До сообщения о готовности проверяется JSON API через Vite.

Сервер слушает localhost. Авторизация включена по умолчанию: регистрация создаёт
изолированное пространство, cookie-сессия защищает API и экспорт. Вход/регистрация:
`/api/v1/auth/login`, `/auth/register`; текущая сессия: `/auth/me`; выход: `/auth/logout`;
смена пароля: `/auth/password`. Изменения требуют `X-CSRF-Token` из ответа сессии.
Старые неразмеченные данные доступны только в явном локальном режиме
`TIREK_AUTH_DISABLED=1` и не открываются произвольному новому пользователю.

## Реализовано

- `/api/v1/health`, задачи, наборы, рекомендации и карточки по общему контракту.
- Изолированные файлы/объекты/idempotency аккаунтов, PBKDF2-пароли, ограничение
  попыток входа, отзыв сессий и журнал автора изменений (`/api/v1/audit`).
- `/api/v1/assistant/status` и `/assistant/chat`: локальная справка или OpenAI
  Responses при настройке `OPENAI_API_KEY` и `TIREK_ASSISTANT_MODEL`.
- `/api/v1/workspace` — дополнительный endpoint навигации: списки наборов, расчётов, утверждений, последний расчёт и возможности.
- Синтетический набор 12 товаров, история полными 28-дневными периодами, индивидуальные профили и явные пропуски. `forecast.method=contract_example`, AI не вызывается.
- Изменение количества с причиной, целочисленность для штучных товаров, MOQ/кратность, защита ревизии.
- Утверждение: серверная проверка состава, бюджета, наличия цен, подтверждения предупреждений.
- Неизменяемые снимки; CSV UTF-8 BOM с `;` и защитой текстовых ячеек от формул.
- SQLite-транзакции и сохраняемая идемпотентность. Незавершённые задачи после перезапуска получают `failed`.
- Загрузка 1–6 XLSX до 30 МБ: проверка типа, содержимого, роли, дублей ролей, размера распакованного XLSX и размеров листа; SHA-256, сохранение исходников и JSON-контекста. Повтор одинакового набора даёт тот же ID.

## Реальная модель и ограничения

Нормализатор и прогноз v2 подключены по умолчанию через `backend.app.ml_adapter`. Неполный набор сохраняется с `calculation_allowed=false`; для полного набора проверяются исходные форматы, а даты и использованные строки берутся из аудита. `/workspace.capabilities` проверяет доступность адаптера и файлов весов, а не возвращает постоянное `true`. Совместимость и хеши весов дополнительно проверяются при прогнозе.

Stockout-интервалы и клиентские метки из `AdditionalContext` подключены к модулю
регулярного спроса. Идентификатор события для метки:
`sales_transactions:<имя листа>:<номер строки Excel>`. Некорректные и противоречивые
ссылки блокируют нормализацию. Без точных входов соответствующая поправка не
выдумывается. Для полного заказа SE используйте подтверждённые колонки
`Минимальная партия` и `Склад` в снимке. Учебные входы создаёт
`scripts/generate_sample_data.py`.

HTTP-мониторинг остатков хранит состояния, переходы порогов 40/30/20% и намерения
пересчёта в SQLite; worker автоматического пересчёта ещё не подключён.
Подтверждённый импорт CSV в конкретную 1С не реализован.
Старая выгрузка IEK без текущего свободного остатка остаётся прогнозом:
количество заказа `null`. Условия MOQ и область склада должны быть подтверждены
до утверждения реальных позиций.

IEK принимает также явный текущий снимок с колонками из `app/inventory_template.py`:
склад, дата, единица/шаг, остаток/резерв/свободный остаток, MOQ/кратность, категория,
цена и поступление/ETA. При полной информации используется тот же decision core,
что у SE. Учебный ZIP: `GET /api/v1/samples?supplier_id=iek` (требует входа),
либо `scripts/generate_sample_data.py --supplier iek --output .local-data/samples-iek`.

LLM-проверка выбранной позиции доступна через POST `/calculations/{id}/items/{item}/ai-review`; провайдер задаётся в `backend/.env`, который читается при старте. Вызов не меняет количества и отвергает результат при изменении ревизии. `request_ai_review=true` проверяет максимум первые пять позиций; отдельная карточка позволяет выбрать другую. Без настроек возвращается `unavailable`. Ключ не передаётся браузеру. [Настройка и реальный прогон](../docs/live-forecast.md).

Синтетический провайдер поддерживает горизонт 28 = 7 + 21 дней. Он не принимает пользовательские экономические/категориальные политики и прирост: изменение этих параметров требует настоящего расчётного модуля. Бюджет применяется к утверждению, а не объявляется оптимизатором.

## Проверки

Из корня:

```powershell
.\.venv-ml\Scripts\python.exe -m pytest backend/tests model -q
.\.venv-ml\Scripts\python.exe scripts/validate_contract.py
```

Тесты используют отдельную временную SQLite-базу: форматы ответов, null/0, MOQ, причины, конфликт ревизии, бюджет и неизвестные цены, предупреждения, повторные запросы, файлы, восстановление после перезапуска и неизменность CSV. Исходный валидатор контракта проверяет спецификацию/примеры отдельно от приложения.

Это не подтверждение AC03–AC07/AC12 для реальной модели. Платформенный путь корректировка → утверждение → экспорт проверяется также Playwright в `frontend/e2e/`.
