# Контракт интеграции команд

Единственный источник HTTP-форматов — [OpenAPI](../contracts/openapi.yaml), версия 1.0.0.
Схема описывает будущую реализацию. Примеры в `contracts/examples/` синтетические.
Команда 1 не должна ждать модель: она начинает с примеров той же схемы.

## API и последовательность

Базовый путь: `/api/v1`. Временный локальный адрес backend: `http://127.0.0.1:8000`.
Адрес frontend: `http://127.0.0.1:5173`. CORS разрешает согласованный frontend origin;
любой другой порт согласуется в начале. API-ключи LLM остаются только на backend.

| Метод и путь | Назначение | Когда нужен |
| --- | --- | --- |
| GET /health | Готовность, доступные поставщики, горизонты, лимиты файлов | T+45 |
| POST /datasets/import | Импорт XLSX, ответ 202 Job | T+90 |
| GET /jobs/{job_id} | Прогресс импорта/расчёта | T+90 |
| GET /datasets/{dataset_id} | Роли источников, даты, качество | T+90 |
| POST /calculations | Запуск расчёта с индивидуальными профилями | T+90 baseline; T+150 ML |
| GET /calculations/{calculation_id}/recommendations | Метаданные, список и основания | T+90 |
| GET /calculations/{calculation_id}/items/{item_id} | Карточка, история, прогноз, факты | T+150 |
| PATCH /calculations/{calculation_id}/items/{item_id} | Ручное количество с причиной и ревизией | T+190 |
| POST /calculations/{calculation_id}/approve | Проверка и фиксация снимка | T+190 |
| GET /approvals/{approval_id}/export.csv | Скачать неизменяемый утверждённый результат | T+190 |

После успеха Job содержит resource_type и resource_id: dataset либо calculation.
Процент выполнения может быть null, если точная оценка невозможна; stage обязателен.

## Единые соглашения

- ID — строки. Коды товаров — строки без удаления ведущих нулей.
- Даты — `YYYY-MM-DD`, отметки времени — ISO 8601 с часовым поясом. Учётные дни для
  исходных данных интерпретируются в Asia/Almaty. Часовой пояс указывается в DatasetReport.
- Количества — числа в явно указанной единице. Для штучных товаров целочисленность
  проверяет backend. Деньги — KZT, одна согласованная база затрат; в MVP JSON numbers,
  внутри backend Decimal для денежных проверок. Денежное округление до 0.01.
- `null` значит неизвестно/не рассчитано; `0` — измеренное или рассчитанное нулевое значение.
- Все расчёты имеют mode, dataset_version, data_as_of, model_id, policy_version, revision.
- forecast.method: `ml`, `baseline`, `contract_example`. Последнее используется только
  синтетическими файлами контракта, не является методом реального расчёта.
- Forecast описывает весь заявленный горизонт. p10/p50/p90 — квантили, не три независимых
  показателя уверенности; порядок p10 ≤ p50 ≤ p90 обязателен.
- order_cost_kzt и marginal_value nullable: их нельзя формировать без входных затрат.
- policy_basis: `economic` либо `service_policy`; отсутствие цен не отменяет базовый
  расчёт при наличии явной политики. category_policies и growth_adjustments — входы
  расчёта, AdditionalContext — вход импорта для stockout, клиента, цены и ведомости.
- decision_status: `ready`, `no_order`, `needs_data`, `needs_review`.
- urgency: `low`, `normal`, `high`, `critical`, `unknown`.
- ai.status: `reviewed`, `not_requested`, `unavailable`; при reviewed обязателен verdict.
- Категории исходника хранятся как category_raw. Значение «1» не объявляется автоматически
  классом A или требованием 99% доступности.

## Корректировка и утверждение

PATCH изменяет final_quantity, сохраняет override_reason и повышает revision. Система
сохраняет исходное recommended_quantity. Значение null в final_quantity означает
исключение позиции из утверждения, причина при этом также обязательна.

POST approve передаёт expected_revision и selected_item_ids. Выбираются только позиции
с известным валидным final_quantity. Для needs_review требуется явно записанное
acknowledged_issue_codes, которое не отменяет жёсткие ограничения. needs_data с
неизвестными критичными входами утверждать нельзя даже ручным вводом количества.

Сервер заново проверяет бюджет, количество, партии и неизменность версии. Новая загрузка
не мутирует старый расчёт; интерфейс должен показать, что существует более свежий набор.
Снимок содержит source mode и все версии. Отправка поставщику отсутствует.

## Ошибки

Единый ответ: `error.code`, `error.message`, `error.details`, `request_id`.
Основные коды: INVALID_FILE, MISSING_SOURCE, UNSUPPORTED_HORIZON, INVALID_PARAMETERS,
MISSING_CRITICAL_DATA, MOQ_VIOLATION, BUDGET_EXCEEDED, PRICE_REQUIRED_FOR_BUDGET,
STALE_REVISION, IDEMPOTENCY_CONFLICT, NOT_FOUND, INTERNAL_ERROR.

HTTP: 400 неверный файл; 404 неизвестная сущность; 409 конфликт версии/ключа;
413 превышение лимита; 422 неверные параметры/ограничения; 500 ошибка сервера.
Ошибка конкретной позиции обычно входит в item.issues и не обнуляет весь список.

## Примеры и синхронизация

`calculation-request.json` — запрос; `job-succeeded.json` — завершённая задача;
`dataset-report.json` — отчёт; `recommendations.json` — таблица;
`item-detail.json` — карточка; `approval.json` — снимок; `error.json` — ошибка.
Дополнительный контекст, корректировка и запрос утверждения также имеют отдельные примеры.
Пример approval относится к исходной revision=1. После выполнения примера PATCH
backend вернёт revision=2: для следующего утверждения нужно передать эту новую ревизию.
Примеры не содержат партнёрских исходных продаж и не подтверждают запуск модели.

Порядок проверки контракта и ограничений примеров: [contracts/README.md](../contracts/README.md).

Изменение обязательного поля/enum согласуется обеими командами. Одним коммитом обновить
OpenAPI, затронутые примеры и клиент. До согласования допускаются только добавления
необязательных полей, которые не меняют смысл существующих. В T+15 контракт замораживается
для основной ветки реализации; после T+190 несовместимые изменения запрещены.
