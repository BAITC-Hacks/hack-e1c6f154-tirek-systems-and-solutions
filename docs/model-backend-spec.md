# Команда 2: ТЗ данных, модели, расчёта и бэкенда

## Ответственность и предлагаемый стек

Наша команда владеет импортом, хранилищем, обучением/оценкой, математикой заказа,
ИИ-проверкой, API, утверждением и экспортом. Предлагаемый стек: Python, FastAPI,
Pydantic, pandas/openpyxl для чтения, CatBoost для первого ML-кандидата, SQLite
для метаданных и локальные файлы для наборов/моделей. Разместить в `backend/`.

За четыре часа достаточно одного процесса и одного рабочего потока задач с защитой
от параллельной мутации. Статусы и версии сохранять; незавершённые задачи после
перезапуска помечать ошибкой, а не оставлять навечно в `running`. Celery/Redis и
развёртывание облачной инфраструктуры в MVP не требуются.

## Модули и зависимости

`ingestion → canonical data → features/forecast → replenishment → judgement → approval/export`

API вызывает эти модули, не содержит копию математики в обработчиках. Модель и расчёт
должны запускаться без UI и без LLM. API-ключ LLM хранится только в окружении сервера.

Быстрый путь `inventory event → stock level → transition` проверяет пороги 40/30/20%
без ожидания ML или LLM. Транзакции, версии, дедупликация и гистерезис описаны
в [stock-monitoring.md](stock-monitoring.md).

Рекомендуемая структура будущей реализации:

```text
backend/app/api/          HTTP и схемы
backend/app/ingestion/    фиксированные адаптеры исходных XLSX
backend/app/data/         нормализованные типы, версии, качество
backend/app/forecast/     baseline, признаки, ML, временная проверка
backend/app/decision/     партии, экономика, поступления, проверки
backend/app/judgement/    LLM-адаптер, схема и доказательства
backend/app/storage/      наборы, задачи, расчёты, снимки
backend/tests/           сценарии приёмки
```

## Импорт и канонические данные

Читать файлы только из каталога загрузки/`DATA_DIR`; исходники не изменять. Для HTTP-импорта
ограничить размер, число и тип файлов. Состав и содержимое XLSX — входные данные,
не команды для приложения или LLM. Рассчитывать хеш содержимого и версию набора.

| Роль | Файл SE | Как используется |
| --- | --- | --- |
| `sales_transactions` | Динамика продаж_Syseme Electric_2025-2026.xlsx | Дата, документ, код, количество, единица, склад |
| `sales_monthly` | Ежемесячные продажи в кол-м выражении SystemElectric 2024-2026.xlsx | Сверка, более ранняя агрегированная история |
| `stock_monthly` | Ежемесячные остатки SystemElectric 2024-2026.xlsx | Контекст доступности; не точный stockout |
| `seasonality` | Сезонность SystemElectric 2024-2026.xlsx | Сезонный контекст и сверка |
| `moq` | MOQ SystemElectric.xlsx | Кратность и сопоставление артикулов |
| `current_stock_inbound` | Товар в пути_SystemElectric на 22.09.2026.xlsx | TDSheet: категории, запас, резерв, ETA и рост |

Нормализованные сущности:

- `products`: supplier_id, sku, supplier_article, name, unit, warehouse_id, category_raw;
- `sales`: source_event_id, source_row_id, event_time, ingested_at, sku, warehouse_id,
  quantity, document_type, nullable pseudonymous_client_id, return/correction flag;
- `inventory`: sku, warehouse_id, snapshot_at, on_hand, reserved, free_stock, provenance;
- `inbound`: sku, warehouse_id, quantity, expected_at, order_id, status, provenance;
- `constraints`: min_order_qty, order_multiple, unit_conversion, provenance;
- `economic_profiles`: sku, horizon, underage_cost, overage_cost, nullable unit_cost,
  source_kind, rationale, effective_from;
- `availability`: sku, date/interval, availability state, observed/estimated origin;
- `quality_issues`: code, severity, source, affected_skus, description, required_action.

При импорте принимать optional JSON context по схеме AdditionalContext: клиентские
метки событий, наблюдаемые интервалы stockout, цены и материальные потребности из 1С.
В расчёте принимать category_policies и growth_adjustments. Поле категории должно
участвовать в выборе политики; внешний прирост применяется к прогнозу явно, с источником
и периодом действия, отдельно от исторического тренда. Потребность ведомости добавлять
только в неучтённой/незарезервированной части и к соответствующей дате. См. MH1–MH5.

Сохранять коды строками, включая ведущие нули и суффиксы. Удалять итоговые строки,
распознавать многострочные заголовки. Не применять `abs()` ко всем продажам. Повторы
документов между источниками сопоставлять по ID/строке; одинаковые по значениям строки
внутри документа не удалять без доказательства дублирования.

Отчёт обязан показывать вклад каждого источника и причины расхождений. Сводные продажи
сверяются с детализацией, а не добавляются к ней. Пропуски остатков не заменяются нулём.
Индексы сезонности, рассчитанные по обороту поставщика, не считать без проверки
индексами количественного спроса каждого товара.

## Baseline и ML

1. Построить baseline регулярного спроса на доступных полных периодах; явно описать
   обработку возвратов, неполного месяца, редких продаж и отсутствующей доступности.
2. Первый ML-кандидат: общая модель CatBoost по товарам. Цель — будущий регулярный
   спрос на выбранном горизонте; код товара/группа, лаги, прошлые скользящие статистики,
   календарь, устойчивый тренд и признаки аномалий доступны на момент прогноза.
3. Минимум два последовательных временных среза, если достаточно истории. Конец каждого
   обучающего target-окна не позже cutoff. Никакого случайного split по строкам.
4. Оценка: MAE/смещение по товарам, WAPE только по сопоставимым группам с ненулевой
   суммой спроса, качество выбранных квантилей при наличии достаточной проверки.
5. Для диапазонов использовать валидированную квантильную модель либо распределение
   ошибок прогноза на полном горизонте, полученное вне обучающей выборки. Не объявлять
   формальную калибровку без измерения покрытия; размер выборки и ограничения сохранить.
6. Сравнить с baseline. Модель не обязана выиграть на всех товарах. Выбранный метод
   и причина переключения видны в ответе. Не выдавать baseline за ML при сбое обучения.

В первом рабочем прогоне допустим горизонт 28 дней. Поддержка дополнительных горизонтов
объявляется только через реализованные `supported_horizons` в health. Условие расчёта:
`horizon_days = lead_time_days + review_period_days`; недопустимую комбинацию отклонить.

Stockout-коррекция возможна только при наблюдаемой доступности или отдельно помеченной
оценке. На текущих реальных источниках нельзя утверждать точные дни отсутствия.
Аномалии реальных продаж выявляются по товару/документу; клиентская агрегация проверяется
отдельно на синтетике, пока pseudonymous_client_id не предоставлен.

Практический baseline: оценивать спрос на доступный день по сопоставимым полным неделям,
учитывать календарь и сезонный профиль, оценённый только по прошлому. Для редких продаж
разделять частоту ненулевых событий и размер такого события: медиана всех дней может
необоснованно дать ноль. Stockout-дни исключать из знаменателя доступных дней;
утраченный спрос оценивать отдельно и сохранять происхождение. Для полностью отсутствующей
доступной истории — аналог категории с предупреждением или needs_data.

Выброс сначала кандидат: робастное отклонение объёма по SKU и доля одного клиента
в коротком окне. Проверить повторяемость по неделям и охват клиентов, чтобы не удалить
устойчивый рост. Разбитые документы одного клиента объединять до проверки; пороги
и окно зафиксировать в версии правил и проверить на контрольных сценариях. Исключение
разовой продажи влияет на regular_sales, но не удаляет исходное событие из хранилища.

## Индивидуальные решения и обновление

Реализовать модель потерь из общего ТЗ. При отсутствии экономических затрат использовать
явную категориальную политику квантиля (`service_policy`), сохраняя экономику null.
Если нет ни экономического профиля, ни политики, либо отсутствует актуальный запас/
срок поставки, поставить `needs_data`; количество остаётся null. Допустимы явно
введённые индивидуальные сценарные профили. Отсутствующий MOQ даёт needs_review;
базовую потребность рассчитывать в единицах товара, не объявляя неизвестную партию равной 1.

Учитывать своевременные поступления по датам. Если дефицит наступает до обычного срока
поставки, показать срочность/необходимость ускорения: стандартный заказ не устраняет
уже возникший разрыв. MOQ и кратность валидировать на итоговой партии. Резерв не вычитать
повторно, если исходный free_stock уже его учитывает.

На MVP пользователь повторно импортирует данные и запускает пересчёт. Это обновляет
прогноз по свежим признакам и рекомендацию без обязательного переобучения. Переобучение
вызывается отдельной локальной командой. «Непрерывное самообучение» не заявляется.

Контроль общего бюджета обязателен, если budget_kzt задан: неизвестные закупочные цены
не считаются нулевыми, превышение блокирует утверждение. Автоматический глобальный
оптимизатор бюджета в MVP не обещается.

## ИИ-проверка

LLM получает компактный пакет: прогноз, экономику, данные о запасе/поставке, диагностические
флаги, применимые правила и список evidence_id. Выход: verdict, reasons, evidence_ids,
rule_ids, suggested_action. Допустимые verdict: supports, needs_review, recalculate.

LLM не меняет количества напрямую. Предложение превращается в параметры нового
проверяемого расчёта; исходный расчёт сохраняется. Проверять JSON, допустимые ID,
наличие фактов и отсутствие неподтверждённых чисел. Произвольный confidence 0–100 не вводить.

Предлагаемый предел: один короткий retry после сетевого сбоя; timeout и ошибка схемы
дают `unavailable`. Использовать пакетирование/ограничение параллелизма; обязательные
проверки доступны без LLM. Для демонстрации достаточно реального разбора выбранных
исключений. Остальные позиции получают `not_requested`, а не фиктивное одобрение.

## API, хранение и экспорт

Реализовать `contracts/openapi.yaml`. Dataset, Job, Calculation и Approval — разные
сущности. Dataset неизменяемый; расчёт ссылается на его версию и параметры.
Редактирование позиции увеличивает revision. Утверждение требует expected_revision
и фиксирует immutable snapshot. Экспорт читает snapshot, а не текущую изменяемую таблицу.

Idempotency-Key на создании задач и утверждении: тот же ключ с тем же запросом возвращает
ту же сущность; тот же ключ с другим содержимым → 409. Эту гарантию сохранять в SQLite.
Изменение количества также требует expected_revision; два клиента не должны терять изменения.

Набор по умолчанию допускает одну демонстрационную рабочую область на локальной машине.
Это не многопользовательский защищённый SaaS. Без аутентификации слушать localhost;
для удалённой демонстрации требуется согласованный доступ, ключи не передаются браузеру.

CSV: UTF-8 с BOM, разделитель `;`, согласованные числовые значения и единицы. Колонки:
approval_id, calculation_id, revision, mode, data_as_of, supplier_id, sku, name, unit,
recommended_quantity, final_quantity, override_reason, urgency, reason, model_id,
policy_version, economics_source. Текст, начинающийся с формульных префиксов Excel,
экспортировать безопасно как текст. Исходные расчётные числа сохранять числами.

## Проверка и готовность

- Повторить AC01–AC12 из общего ТЗ; сохранить результаты и ограничения в `backend/README.md`.
- Добавить осмысленные тесты: инварианты запасов/поступлений, партии, пропуски, бюджет,
  клиентский выброс, stockout, временные срезы, revision и snapshot/export.
- Для синтетического выброса сравнивать с тем же набором до вставки, включая повторное
  выполнение выделения регулярного спроса. Для stockout известный latent demand хранится
  только в тестовой истине, не подаётся в признаки.
- Задокументировать воспроизводимые команды запуска/импорта/обучения/оценки, переменные
  DATA_DIR и LLM-провайдера, даты train/validation, выбранный метод и аппаратную среду.
- Измерить время импорта, прогноза, расчёта и ИИ отдельно. Предварительная цель UX:
  экран остаётся отзывчивым и всегда показывает состояние задачи; абсолютное время
  расчёта фиксируется после первого измерения, а не обещается заранее.
