# Исходный кейс и матрица выполнения

Актуальная проверка пяти must-have после подключения аккаунтов, контекста спроса
и текущего снимка IEK: [проверка MVP](mvp-verification.md). Ниже сохранены исходные
критерии и результаты предыдущего этапа; они не заменяют новый отчёт о проверке.

Источник требований: кейс HackAlem AI партнёра ТОО «Электрокомплект»,
«Автоматический расчёт заказов поставщикам для пополнения склада», повторно
подтверждённый командой 23.09.2026. Этот документ имеет приоритет при сокращении MVP.

## Проблема, пользователь и ценность

Менеджер закупок вручную объединяет Excel и рассчитывает пополнение слишком редко.
Результат — излишки, дефицит, упущенные продажи; крупные разовые покупки искажают
регулярную потребность. Ценность: сократить хранение излишков и дефицит, повысить
точность регулярных решений, удобство и скорость работы менеджера.

Сценарий исходного кейса: запуск по складу или категории → список заказов с
обоснованием → проверка/корректировка → утверждение → совместимый экспорт.

## Пять обязательных требований

| ID | Требование исходного кейса | Команда 2: реализация | Команда 1: представление | Доказательство приёмки |
| --- | --- | --- | --- | --- |
| MH1 | Базовая потребность по артикулу с учётом истории, текущих остатков, пути, категории и прогноза прироста; переданные источники не игнорируются | Канонические входы, политики категорий, внешний growth_adjustment, расчёт запаса и поступлений | Выбор склада/категории, параметры, источники, количество | Контрольные сценарии меняют по одному входу; фиксируются forecast/target/quantity и причины изменения |
| MH2 | Сезонность и устойчивый рост спроса | Временные признаки, сезонный baseline/ML, отделение тренда от выброса | История, прогноз и объяснение факторов | Сезонный ряд сохраняет паттерн; устойчивый рост повышает ожидаемый спрос |
| MH3 | Оценка и компенсация упущенного спроса при stockout | Вход интервалов доступности; оценка по доступным периодам/аналогам; оценённые значения помечаются | Показать наблюдаемые продажи и поправку отдельно | В тесте с известным stockout расчётная потребность выше сырого варианта |
| MH4 | Исключение разовых крупных заказов, в том числе одного клиента | Группировка по обезличенному клиенту и товару в окне, проверка повторяемости; отделение разового спроса | Причина исключения, объём, даты, обезличенный ID | Вставить разовую покупку x10, в том числе разбитую на несколько документов одного клиента; регулярная рекомендация существенно не растёт |
| MH5 | Итог по поставщикам, обоснование каждой позиции | supplier_id/name, SKU, quantity, reason, urgency, provenance в ответе и CSV | Группировка по поставщикам, объяснение, корректировка, утверждение | Тест минимум с двумя синтетическими поставщиками; каждая строка объяснена и попадает в правильную группу |

Тест MH1 подбирается так, чтобы изменение не скрывалось округлением, нулевой потребностью
или действующим ограничением. Для обычных данных малое изменение входа не обязано
менять целочисленную партию; промежуточное влияние и происхождение остаются наблюдаемыми.

Для MH4 предварительная допустимая разница регулярного количества — не более max(10%
исходного количества, одна минимальная единица/партия) на выбранном контрольном примере.
Зафиксировать порог до запуска проверки. Проверять и прогноз, и конечное количество.

## Входы: что поддержать и что имеется сейчас

| Вход кейса | Наличие в текущих файлах | Путь реализации/проверки |
| --- | --- | --- |
| Дата, код, название, количество, склад | Есть в детализации | XLSX-адаптер |
| Цена продажи | Полного достоверного набора нет | Нормализованный дополнительный контекст; без цены доступны количество и базовая политика |
| Обезличенный клиент | Нет в детализации | context.client_labels связывает событие и pseudonymous_client_id; реалистичный тестовый набор |
| Текущие остатки по складам | SE: сводный файл; IEK: недостаточно | SE основной путь; отсутствие актуального остатка у IEK явно показать |
| История остатков/stockout | Месячные остатки есть, точных интервалов нет | Месячные признаки доступности без выдуманных дат; context.stockout_intervals для точной проверки |
| Поставщик и срок поставки | Поставщики известны; есть ETA некоторых заказов | supplier_id и явные параметры срока; ETA открытого заказа не считать сроком нового |
| Материальная ведомость из 1С | Отдельный формат не предоставлен | context.material_requirements: SKU, количество, срок, ссылка на строку; вычесть уже учтённую/зарезервированную часть |
| Категории | Есть числовые категории SE, расшифровки нет | category_raw и явно введённые category_policies; не изобретать значение кодов |
| Прогноз прироста | Есть исторические коэффициенты, внешний прогноз не подтверждён | growth_adjustments с rate, периодом, источником; исторический тренд отдельно |
| Сезонность | Есть файлы | Включить в текущий контекст; в backtest пересчитывать только по прошлому |

Дополнительный контекст загружается JSON-полем `context` вместе с XLSX (схема
AdditionalContext в OpenAPI). Это адаптер нормализованных данных, не живая интеграция
с 1С и не универсальный парсер неизвестного формата ведомости.

Синтетика разрешена исходным кейсом и должна иметь реалистичное распределение,
сохранять отдельный dataset/version/mode и не выдаваться за выгрузку партнёра.

## Ограничения и обязательные артефакты

- Клиентские признаки только обезличенные. ФИО, телефоны, адреса не нужны модели и не
  должны попадать в признаки, LLM-контекст, репозиторий и примеры.
- Без подтверждения сотрудника заказ не отправляется. В MVP отправка отсутствует;
  утверждение создаёт только снимок для экспорта.
- Каждая рекомендация объяснима и сохраняет версии данных, модели, правил и допущений.
- Схема CSV заранее доступна; совместимость с конкретным импортом 1С требует образца
  или сверки у партнёра. Не заявлять подтверждённый round-trip, пока такой проверки нет.
- Репозиторий и README обязательны: методология, исключение выбросов, запуск, проверки,
  фактические метрики и известные ограничения.

## Опциональные функции исходного кейса

Приоритизация риска дефицита, MOQ/условия поставщика, графики по категориям и
автоматическая выгрузка/рассылка. MOQ удобно включить, поскольку справочники уже есть,
но отсутствие MOQ не блокирует базовый прогноз и потребность: это needs_review,
неизвестное условие и явное подтверждение менеджера. Округление по единице измерения
не означает, что минимальная партия поставщика известна.

Динамический экономический скоринг, ML и ИИ-проверка — согласованное развитие решения.
Они дополняют пять must-have. Матрица нужна, чтобы за четыре часа не заменить исходный
кейс демонстрацией красивой модели без stockout, клиентских выбросов и готового списка заказов.
