# Анализ готовности к просмотру жюри

Дата: 23.09.2026. Организационные условия переданы командой в сообщении при
подготовке README. Бизнес-анализ опирается на [матрицу кейса](requirements-matrix.md),
код и сохранённые отчёты.

## Условия организаторов

Жюри должны самостоятельно понять продукт. Все четыре требуемых пункта
вынесены в [корневой README](../README.md).

| Требование | Что подготовлено |
| --- | --- |
| Что решает продукт | Проблема закупщика, сценарий, ожидаемая ценность и ограничения |
| Как запустить | Зависимости, clone, Windows / Linux / macOS, адреса, остановка и диагностика |
| Какие технологии | Таблица стека, схема обработки данных и ссылки на модули |
| Как проверить | Пятиминутный сценарий, ожидаемые результаты, CSV, тесты и проверка XLSX |

Отдельное правило из сообщения: если проект готов раньше, продолжать развитие;
уходить до **18:00 запрещено**. Это обязанность команды на площадке;
репозиторий не подтверждает её выполнение.

## Фактическое покрытие бизнес-кейса

| Требование | Реализация и доказательство | Граница готовности |
| --- | --- | --- |
| MH1: история, остаток, путь, категория и прирост | [Адаптер](../backend/app/ml_adapter.py), [ядро](../model/decision/core.py), [тесты](../backend/tests/test_ml_adapter.py) | Веб-путь SE / Алматы / шт.; нужны актуальные данные и политики. Неизвестные MOQ и область склада не считаются подтверждёнными |
| MH2: сезонность и устойчивый рост | [Прогноз v2](../model/forecast_v2/README.md), [регулярный спрос](../model/regular_forecast/README.md), временные проверки | Зафиксированы фактические ошибки; нужен новый независимый holdout |
| MH3: компенсация stockout | [Отдельный прогноз](../model/regular_forecast/predictor.py), [тесты](../model/regular_forecast/test_predictor.py) | Синтетическая доступность; не подключено к реальному HTTP-прогнозу, точных интервалов в выгрузке нет |
| MH4: разовые крупные заказы клиента | Семидневные клиентские окна, аудит исключённого объёма, тесты разовых и повторяемых покупок | В выгрузке нет обезличенного клиента; алгоритм отдельный, доказательства на партнёрских данных нет |
| MH5: поставщики и обоснования | Группировка UI, причины, provenance, корректировки, утверждения, CSV | Реальный адаптер — SE; ядро поддерживает группировку, IEK пока офлайн |

Полное выполнение пяти требований на реальных данных пока не подтверждено.
Демо проверяет пользовательский цикл без доступа к файлам партнёра;
оно не доказывает точность модели.

## Качество и методология

- У v2 на SE WAPE **33,92%** против **37,73%** у baseline v1.
  Это сравнение на одинаковых данных; цель WAPE ≤10% не достигнута.
- Два evaluation-окна просматривались при разработке v1: это ретроспективная
  повторная оценка, не новый независимый тест.
- SE / штуки и три панели IEK оцениваются раздельно. Положительные продажи
  не равны скрытому спросу с учётом stockout и проектов.
- У отдельного синтетического testbed финальный WAPE baseline **25,85%**;
  54/54 бизнес-примеров относятся к его reference-функции, а не автоматически
  к расчётному адаптеру платформы.
- Веса, SHA-256, протоколы и агрегированные отчёты есть в Git.
  Для повторения обучения нужны партнёрские XLSX, которые не публикуются.

Источники: [отчёт v2](../model/forecast_v2/REPORT.md),
[результаты testbed](../model/testbed/RESULTS.md).

## Проверки перед сдачей

[Команды воспроизведения](../README.md#автоматические-проверки).
Локальное окружение: Windows, Python 3.12.14, Node.js 20.19.0.
Проверка выполнена после интеграционного коммита `597928c`.

| Проверка | Результат |
| --- | --- |
| `python -m pytest backend/tests model -q` | 173 теста и 763 subtests прошли; одно предупреждение Starlette об устаревающей поддержке httpx в TestClient |
| `python scripts/validate_contract.py` | Две OpenAPI-схемы, 12 примеров, согласованность примеров и ссылки в 14 Markdown-файлах проверены |
| `npm --prefix frontend run build` | TypeScript и production-сборка Vite прошли |
| Проверка зависимостей через `uv pip check` | 57 установленных пакетов совместимы |
| `git diff --check` | Ошибок форматирования diff нет |

В [аудите интеграции](integration-audit.md) отдельно зафиксированы 11 пройденных
сценариев Playwright и smoke-проверка загрузки весов. При подготовке документации
эти проверки повторно не запускались. Полный импорт партнёрских XLSX в текущем
окружении не проверялся: исходных файлов здесь нет. Linux/macOS не проверялись.

## Что развивать дальше

1. Подключить регулярный спрос со stockout и клиентскими окнами к HTTP-пути;
   получить точную доступность и обезличенные клиентские события.
2. Подтвердить актуальность и область склада, MOQ, цены и сроки поставки;
   провести реальный цикл до утверждаемой партии.
3. Проверить прогноз на новых периодах, измерить влияние на дефицит,
   излишки и время подготовки заказа.
4. Расширить реальный адаптер на IEK, сверить CSV с импортом партнёра в 1С.
5. Добавить авторизацию и изоляцию пользователей перед общим развёртыванием.
