# План работы двух команд на 4 часа

Статус: предлагаемый план v1 от 23.09.2026. T+0 — совместный старт реализации.
Численность команд неизвестна: ниже указаны роли, один человек может совмещать несколько.
Сначала прочитать этот файл и [матрицу исходного кейса](requirements-matrix.md), затем своё ТЗ и правила интеграции.

## Результат к T+240

Один воспроизводимый сценарий: загрузить данные Systeme Electric, запустить расчёт,
увидеть прогноз и рекомендации с основаниями, изменить количество с причиной,
утвердить результат и скачать CSV. Показать, как свежие данные и индивидуальная
экономика товара меняют рекомендацию. Указать, где реальный факт, сценарное
допущение и синтетический пример. Наличие ML и ИИ показывать только при их фактическом запуске.

## Разделение ответственности

| Область | Команда 1: платформа | Команда 2: модель и бэкенд — мы |
| --- | --- | --- |
| Пользовательский сценарий, экраны, UX | Владелец | Проверка реализуемости |
| Загрузка, таблица, карточка товара, график | Владелец | Предоставляет данные API |
| Очередь задач, хранение, HTTP API, CSV | Интегрирует клиент | Владелец |
| Импорт, нормализация, качество данных | Показывает отчёт | Владелец |
| Baseline, обучение и оценка ML | Показывает метод и метрики | Владелец |
| Индивидуальная экономика, партии, поступления | Ввод параметров | Владелец расчёта и валидации |
| ИИ-проверка | Показывает заключение | Владелец вызова, схемы и отказоустойчивости |
| Контракт и синтетические примеры | Совместное согласование | Владелец схемы, совместное согласование изменений |
| Утверждение и изменение количества | Интерфейс | Проверки, версии, неизменяемый снимок |
| Запуск и итоговая демонстрация | Фронтенд и сценарий | Бэкенд, данные, модель; совместная проверка |

Роли для команды 1: интерфейс; API-интеграция и проверка сценария.
Роли для команды 2: данные/ML; API/расчёт/ИИ. При нехватке людей сокращать функции,
сохраняя рабочий сквозной сценарий. Контакт по интеграции назначается от каждой команды.

## Расписание

| Интервал | Команда 1 | Команда 2 | Обязательный результат |
| --- | --- | --- | --- |
| 0–15 мин | Согласовать три экрана, статусы и контракт | Выбрать набор данных, параметры сценария, подтвердить контракт | Зафиксированы поля, адрес API, роли, один демонстрационный набор |
| 15–45 мин | Каркас UI и клиент API; синтетические ответы | Каркас API и задачи; импорт SE; отчёт качества | Платформа показывает примеры; API отвечает на health |
| 45–90 мин | Загрузка, polling, группировка по поставщику и карточка | Baseline, категории/прирост, поступления, stockout и выбросы на тестовых данных | Реальный импорт → baseline → таблица через API; пять must-have имеют исполнимый путь |
| 90–150 мин | Настройки товара, объяснения, ошибки, график | Обучить одну ML-модель, провести временную проверку; индивидуальная экономика | ML-результат сравнен с baseline; различаются индивидуальные решения |
| 150–190 мин | Корректировка, утверждение, экспорт | ИИ-проверка, снимки утверждения, CSV; повторный расчёт | Полный сценарий и корректный отказ ИИ |
| 190–220 мин | Общая проверка и устранение ошибок | Приёмочные сценарии, документация запуска и результатов | Один чистый прогон на согласованной машине |
| 220–240 мин | Репетиция демонстрации | Стабилизация, фиксация версии | Демонстрация без новых функций |

## Контрольные точки и сокращение объёма

- T+45: если API не готов, UI продолжает с примерами; формат больше не меняем без согласования.
- T+90: если нет общего сценария, обе команды переключаются на интеграцию. Новые экраны и модели откладываются.
- T+150: если ML не обучен, baseline остаётся доступным с честной маркировкой. Это частичное выполнение ML-части, а не готовая ML-система.
- T+170: при отсутствии ключа/доступного LLM показываем «ИИ-проверка недоступна». Детерминированные проверки продолжают работать; они не называются ИИ.
- После T+190: никаких новых интеграций, моделей и экранов. Только исправления, критерии приёмки и демонстрация.

Приоритет сокращения: реальный импорт IEK → дополнительные графики → расширенные фильтры → дополнительная модель → расширенный экономический оптимизатор.
Сохраняем импорт SE, один расчёт, объяснение происхождения чисел, корректировку, утверждение и CSV.
Пять must-have, включая stockout, клиентские выбросы и группировку по поставщикам,
не переводятся в опциональные функции. Ограничения реальных данных компенсируются
отдельным реалистичным тестовым набором, разрешённым условием кейса.

## За рамками четырёх часов

Живые Kaspi/1С/UMAG, сторонняя рыночная аналитика, мультиарендность, полноценные роли
пользователей, автоматическое переобучение по расписанию, распределённые очереди,
оптимизация нескольких складов и поставщиков. Архитектурные границы для них описаны,
но не заявляются как реализованные возможности.

## Работа в Git

- Команда 1: `frontend/**`; команда 2: `backend/**`, `tests/**`, `scripts/**`.
- `contracts/**` и общие документы меняются согласованно, владельцем контракта выступает команда 2.
- Рекомендуемые ветки: `codex/platform`, `codex/model-backend`; интеграционный владелец переносит проверенные изменения в `main`.
- Маленькие законченные коммиты; в сообщении описать что сделано, зачем и как проверено.
- Не коммитить исходные партнёрские данные, секреты, модели большого размера и локальные выгрузки.

## Приёмка на демонстрации

1. Показать дату данных и полный отчёт импорта.
2. Показать отличие ML от baseline и честные ограничения проверки.
3. На двух товарах показать различную стоимость дефицита/излишка и различное решение.
4. Добавить своевременное поступление: потребность не увеличивается.
5. Увеличить остаток: потребность не увеличивается.
6. Показать ИИ-заключение со ссылками на факты либо реальный статус недоступности.
7. Исправить количество с причиной, утвердить, скачать соответствующий снимку CSV.
8. Отдельно выполнить синтетические проверки stockout и крупного заказа одного клиента.
