## Что выполнено 23.09.2026

веса forecast v2, без переобучения и подмены примерами. Расчёт сохранён в рабочей
SQLite и виден в интерфейсе как наблюдаемые источники, операционный режим, метод ML.

Дата данных 22.09.2026, прогноз 23.09–20.10.2026 (28 дней).
Это проверка работоспособности на реальных входах, не измерение точности будущего
спроса. Полнота последнего дня неизвестна. Прогноз наблюдаемых продаж не исправляет
скрытый спрос при stockout и не исключает клиентские разовые заказы.

Источники, промежуточные данные, названия товаров и SQLite остаются локально в
`DATA_DIR/uploads` и `DATA_DIR/tirek.sqlite3`, они не публикуются в Git.

## Повторный запуск

1. Запустите `scripts/dev.ps1` с окружением `.venv-ml`.
2. В «Источниках данных» выберите **IEK · прогноз продаж**, загрузите XLSX
   с оригинальными именами. Для прогноза обязательны `Динамика*.xlsx` и
   `Ежемесячные продажи*.xlsx`; остальные роли сохраняются с явным отчётом об использовании.
3. В отчёте нажмите «Перейти к расчёту». Оставьте дату источников и запустите прогноз.
4. Откройте рекомендации: таблица разбита по 50 строк, есть поиск и фильтр поставщика.
   В карточке показаны фактическая история и прогноз. Отсутствующий регулярный ряд
   не скрывает наблюдаемые продажи, отсутствующие интервалы не заменяются нулём.

Для локального импорта через тот же API:

```powershell
.\.venv-ml\Scripts\python.exe -X utf8 scripts/import_local.py 'C:\path\IEK' --supplier iek --forecast
```

Динамика IEK содержит более 171 тысяч строк. Лимит листа поднят до 250 тысяч;
ограничения 30 МБ исходников, 120 МБ распакованного XLSX и 256 столбцов сохранены.

Файл «Путь ИЭК» содержит поступления, а не актуальный свободный остаток. Поэтому
прогноз спроса рассчитан, но рекомендуемое количество заказа и стоимость остаются
`null`, утверждение недоступно. Месячные остатки не подменяют текущий снимок.
Экономические политики, категории и прирост в адаптере IEK пока не принимаются;
его назначение явно ограничено прогнозом. SE сохраняет свой расчёт закупки.

## Подключение LLM

Транспорт использует Chat Completions и JSON-ответ с последующей проверкой полей,
ссылок на факты, правил и ревизии. Основа: [OpenAI Docs — JSON mode](https://developers.openai.com/api/docs/guides/structured-outputs#json-mode).
Имена моделей не зашиты: укажите модель, доступную вашему аккаунту.

Создайте локальный `backend/.env` (он исключён из Git):

```dotenv
TIREK_LLM_BASE_URL=https://api.openai.com/v1
TIREK_LLM_MODEL=YOUR_AVAILABLE_MODEL
TIREK_LLM_API_KEY=YOUR_LOCAL_SECRET
```

Можно использовать совместимый локальный endpoint: для localhost ключ необязателен.
После перезапуска сервера `/health.llm_available` показывает наличие конфигурации;
это не обещание доступности внешнего сервиса. В карточке → «Обоснование» →
«Проверить с ИИ» выполняется настоящий вызов провайдера. Внешнему провайдеру
передаётся компактный контекст выбранного товара; полные XLSX не отправляются.

При отсутствии настроек кнопка отключена с объяснением. Успешное заключение
содержит модель, причины и действие. Timeout, HTTP-ошибка, выдуманные evidence/rule ID,
неподтверждённые числа и изменившаяся ревизия не превращаются в одобрение.
ИИ не меняет количество и не утверждает заказ. Автоматическая проверка расчёта
по `request_ai_review=true` ограничена первыми пятью позициями, остальные проверяются
по одной из карточки. На сетевой сбой допускается один повтор.

На этой машине ключ и модель LLM пока не настроены: живой внешний вызов не заявляется.
MockTransport-тесты отдельно проверяют запрос/ответ и отказ при неверных данных.

## Проверки

- 180 Python-тестов и 763 subtests: импорт IEK → настоящие веса → HTTP-ответ;
  сохранение/конфликты ревизий ИИ; существующие правила закупки и модели.
- Production-сборка TypeScript/Vite.
- 13 браузерных сценариев платформы, кнопка ИИ с явным тестовым ответом и график
  наблюдаемых продаж при `regular_sales=null`.
- Отдельная проверка браузером на сохранённом реальном расчёте: 2 149 позиций,
  страницы по 50, карточка ML, исходные данные и мобильный экран без переполнения.
