# Подключение данных, модели и расчёта

Платформенный слой уже реализован. Точки расширения отделены от HTTP, SQLite, утверждения и CSV. Основной формат остаётся `contracts/openapi.yaml`; типы фронтенда генерируются из него.

В [model/](../model/README.md) уже есть обученный CatBoost, baseline, веса и оценка качества. Пока они работают отдельно от платформы. Описанные ниже адаптеры предназначены для их подключения; UI-демо не вызывает эту модель автоматически.

## 1. Нормализатор XLSX

Задайте в окружении процесса backend:

```powershell
$env:TIREK_INGESTOR = 'backend.app.ml_adapter:normalize_dataset'
```

Создайте функцию с интерфейсом:

```python
def normalize_dataset(directory: Path, report: dict, context: dict | None) -> dict:
    # directory содержит файлы sales_transactions.xlsx, sales_monthly.xlsx,
    # stock_monthly.xlsx, seasonality.xlsx, moq.xlsx, current_stock_inbound.xlsx
    # и manifest.json. Некоторые роли могут отсутствовать.
    # Сохранить здесь же канонические таблицы. Исходные XLSX не изменять.
    # Вернуть DatasetReport с фактическими датами, sku_count,
    # rows_used, проблемами и calculation_allowed.
    return normalized_report
```

Перед вызовом платформа проверяет XLSX и сохраняет оригиналы. Ответ нормализатора валидируется по `DatasetReport`; менять `dataset_id` нельзя. Удалите предупреждение `NORMALIZATION_REQUIRED` только после фактической нормализации, `SOURCE_DATE_UNKNOWN` — только при подтверждённой дате. Сохраните проблемы отсутствующих ролей. `calculation_allowed=true` выставляется при достаточных входах.

## 2. Расчётный провайдер

```powershell
$env:TIREK_PIPELINE = 'backend.app.ml_adapter:MyCalculationPipeline'
```

Интерфейс определён в `backend/app/pipeline.py`:

```python
class MyCalculationPipeline:
    def calculate(self, dataset: dict, request: dict, calculation_id: str) -> dict:
        # dataset: DatasetReport.
        # request: CalculationRequest из общего контракта.
        # Прочитать канонические данные из DATA_DIR/uploads/<dataset_id>.
        # Вычислить прогноз, партии, экономику и объяснения на backend.
        return {
            "response": recommendations_response,  # RecommendationsResponse
            "details": {item_id: item_detail},     # ItemDetail для каждой позиции
            "request": request,
        }
```

Платформа выполняет задачу в фоновом потоке, сохраняет результат и отдаёт его существующему UI. Нельзя обращаться к SQLite-платформе внутри провайдера без необходимости. Длительные расчёты пока показывают стадию, а не выдуманный прогресс по батчам.

Согласуйте `meta.calculation_id`, `dataset_id`, версии, дату, горизонт, режим и `revision=1`. У списка и карточек должны совпадать метаданные и значения позиции. `summary` рассчитывается сервером; вспомогательная функция находится в `backend/app/demo.py`, её можно вынести в отдельный доменный модуль при развитии расчёта.

## 3. Что модель должна вернуть

- Полный горизонт спроса и nullable-квантили, `method=ml` только после действительного запуска модели. Baseline — `method=baseline`.
- Потребность с учётом дат поступлений и ограничений, индивидуальный профиль/политику; отсутствие цены само по себе не обнуляет спрос.
- `null` при отсутствии критичных данных, `0` при настоящем решении не закупать.
- Проблемы, основания `evidence`, корректный статус ИИ. Не придумывать ежедневную траекторию из агрегатов.
- Сохранять исходную рекомендацию. Пользовательская правка остаётся ответственностью платформы.

Для реального набора провайдер не подменяется демонстрационным при сбое. Без `TIREK_PIPELINE` сервер сообщает `PIPELINE_NOT_CONFIGURED`. Для операционного режима запрещены синтетические/смешанные наблюдения и синтетические параметры.

## 4. Проверка подключения

1. Повторно импортировать набор после настройки нормализатора.
2. Проверить `GET /api/v1/datasets/{id}`: происхождение, дата, число кодов, роли, проблемы.
3. Отправить `POST /api/v1/calculations` с `Idempotency-Key` и полным `CalculationRequest`.
4. Дождаться `succeeded` через `/jobs/{id}`.
5. Проверить список и карточки по общему контракту, затем выполнить корректировку, утверждение и CSV.

Браузерный диалог сейчас ориентирован на готовый 28-дневный демосценарий. Для первых интеграционных прогонов реальных моделей используйте HTTP-контракт; дополнительные политики/экономические профили можно затем включить в форму, не меняя API-клиент.

Для восстановления примера доступны `contracts/examples/`; это образцы формата, не результаты обучения. Требования к обучению, временным срезам и бизнес-инвариантам остаются в `model-backend-spec.md` и `decision-rules.md`.
