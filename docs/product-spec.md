# Общее ТЗ: динамические рекомендации по закупке

## Цель и границы

Пользователь — менеджер закупок. Приоритеты: удобство, скорость и качество решений.
Результат — количество к закупке по товару, причины, срочность, ограничения и источник каждого значимого параметра.
Единица решения: товар × склад × дата расчёта × горизонт. Общая математическая логика
использует индивидуальные параметры товара; фиксированного рейтинга «хороший/плохой товар» нет.

MVP на 4 часа ориентирован на Systeme Electric. IEK — следующий этап, если основной сценарий готов.
Предлагаемый стартовый горизонт — 28 дней; другие горизонты доступны только после реализации
и проверки. Backend сообщает поддерживаемые горизонты через `/health`.

## Обязательный сценарий

1. Загрузить шесть XLSX SE либо выбрать локально подготовленный набор.
2. Получить отчёт: источники, даты, пересечения кодов, пропуски, ошибки и доступность расчёта.
3. Указать склад/категорию, дату расчёта, срок поставки, период пересмотра и политику запаса;
   при наличии данных добавить экономические профили товаров и внешний прогноз прироста.
4. Запустить задачу; увидеть прогресс, затем рекомендации и отдельно позиции с нехваткой данных.
5. В карточке увидеть историю, прогноз, текущий запас, поступления, параметры экономики и ИИ-проверку.
6. При необходимости изменить количество с причиной, затем утвердить снимок и экспортировать CSV.

Пустое значение отличается от нуля. При недостатке критичных параметров прогноз можно
показать, но количество заказа остаётся `null` с конкретной причиной. Отсутствие цен
само по себе не блокирует базовое пополнение: используется явно заданная политика
целевого квантиля по категории/товару (`policy_basis=service_policy`). Экономические
показатели остаются null. При наличии подтверждённых затрат используется
`policy_basis=economic`. Это два честно обозначенных способа выбора политики.

## Режимы и происхождение параметров

- `operational`: рекомендации на фактических и явно введённых менеджером параметрах.
- `scenario`: расчёт с синтетическими допущениями, явно обозначенный в интерфейсе и CSV.
- Набор с синтетическими или смешанными наблюдениями тоже требует `scenario`;
  недостаточно проверить только источник экономических параметров.
- Источник параметра: `observed`, `manual` или `synthetic`; к нему прикладывается основание.
- В исходных данных нет полного набора цен и переменных расходов. Поле «СС реал» само по себе
  не подтверждает маржу. Экономические значения нельзя выдумывать или скрытно заменять нулями.
- Для демонстрации разрешён отдельный набор 6–12 индивидуальных сценарных профилей;
  реальные прогнозы продаж и сценарная экономика обозначаются раздельно.
- Утверждение сценария означает фиксацию сценария, а не разрешение отправки реального заказа.

## Математическая модель MVP

Прогнозируется распределение регулярного спроса за горизонт H. Разовые проектные продажи
отделяются от регулярного спроса; подтверждённые будущие обязательства учитываются отдельно
и не дублируют резерв. Сезонность и устойчивый рост входят в прогноз один раз.

Для товара задаются сопоставимые на одном горизонте значения в KZT/ед.:

- `underage_cost`: потеря от нехватки единицы, включая упущенный вклад и обоснованные дополнительные последствия;
- `overage_cost`: потеря от лишней единицы за горизонт, включая хранение, капитал и обесценение с учётом её остаточной ценности.

Аналитический ориентир при отсутствии общих ограничений:

`loss(S) = underage_cost * E[max(D-S, 0)] + overage_cost * E[max(S-D, 0)]`

`target_quantile = underage_cost / (underage_cost + overage_cost)`

`target_stock = quantile(demand_over_horizon, target_quantile)`

Если категория задаёт minimum_target_quantile, используется максимум из экономического
квантиля и этой границы. В service_policy применяется target_quantile категории;
значение ниже заданного минимума отклоняется. Каждая такая граница имеет источник
и основание. Порядок правил и контрольные бизнес-ситуации: [decision-rules.md](decision-rules.md).

Это модель одного периода. В реализации проверяется последовательность остатков и
поступлений по датам; поздняя поставка не покрывает более ранний дефицит. Не добавляем
повторно страховой запас, если риск уже учтён выбранным квантилем. Не суммируем дневные
P90 как P90 суммарного спроса.

Для экономического режима допустимых партий `q` рассчитываются ожидаемые потери и выбирается минимум.
В набор кандидатов входят ноль и количества, удовлетворяющие MOQ/кратности; выбор
проверяется после округления. При необходимости перебор ограничивается разумной верхней
границей, которая видна в диагностике. Ноль допустим при отсутствии обязательств.

Скоринг следующей партии для объяснения:

`marginal_value = (expected_loss_before - expected_loss_after) / additional_capital`

Этот показатель не заменяет проверку общего бюджета и минимальных партий. Если стоимость
капитала/закупки неизвестна, показатель не рассчитывается. Для четырёхчасового MVP общий
бюджет проверяется как ограничение утверждения. Автоматическое оптимальное распределение
бюджета между товарами — следующий этап; нельзя называть простую сортировку таким оптимумом.

## Основные данные и известные ограничения

| Источник | Использование | Ограничение |
| --- | --- | --- |
| Детальная динамика продаж | Регулярный спрос, выбросы, даты, склад | Нет ID клиента; отрицательные количества требуют трактовки |
| Помесячные продажи | История 2024+, сверка и сезонный контекст | Не складывать с детализацией как дополнительные продажи |
| Исторические остатки | Контекст доступности | Месячный снимок не задаёт точные даты stockout |
| Сезонность | Признак/контроль сезонного паттерна | Для backtest коэффициенты пересчитываются только по прошлому |
| MOQ | Минимальная партия/кратность | Эти понятия нельзя автоматически считать одинаковыми |
| Сводный файл SE «Товар в пути» | 497 позиций: категории, остатки, резервы, рост, поступления | Значения категорий требуют расшифровки; существующие формулы проверяются |

Файлы SE содержат 554 кода в помесячных продажах и 701 код в истории остатков; полный
сводный профиль есть не для всех. Несопоставленные позиции остаются в отчёте.
В динамике продаж обоих поставщиков нет ID клиента. У IEK актуальный свободный остаток
не подтверждён историческим отчётом начальных остатков. В исходном сводном отчёте SE
«последние 12 мес» суммируют 13 месячных колонок; формулу не копируем вслепую.

Сентябрь 2026 неполный. Отдельные старые строки в детализации не доказывают полную
детальную историю за 2023–2024 годы. Текущие категории и коэффициенты не подмешиваются
в прошлые срезы как будто были известны тогда.

## Приёмочные требования

| ID | Проверка | Ожидаемый результат |
| --- | --- | --- |
| AC01 | Импорт источников | Все шесть ролей SE представлены в отчёте; потери строк и кодов объяснены |
| AC02 | Свежие данные | Новый набор получает новую версию; неизменённая повторная загрузка не удваивает продажи |
| AC03 | Остаток/поступление | Увеличение свободного остатка или своевременного поступления не повышает потребность при прочих равных |
| AC04 | Сезонность/рост | Контрольный ряд с сезонностью и устойчивым трендом отражён в прогнозе; нет двойного коэффициента |
| AC05 | Stockout | На синтетическом наборе с известной доступностью поправка повышает оценку относительно сырых продаж |
| AC06 | Разовый клиентский заказ | На синтетическом наборе с client_id выброс x10 не повышает регулярный прогноз более согласованного порога; предварительный порог 10%, фиксируется до проверки |
| AC07 | Индивидуальная экономика | При одинаковом спросе рост underage_cost не снижает целевой квантиль; рост overage_cost не повышает его |
| AC08 | Ограничения | Положительное количество соответствует единицам и известным MOQ/кратности; неизвестное условие отмечено needs_review и не превращается в 1 |
| AC09 | Обоснование | Каждая позиция имеет факты, допущения, модель, версию данных и причину рекомендации/отказа |
| AC10 | ИИ | Заключение структурировано и основано на переданных фактах; ошибка LLM показана явно |
| AC11 | Корректировка/экспорт | Причина изменения обязательна; CSV соответствует утверждённому снимку |
| AC12 | ML | Есть фактический запуск обучения, временная проверка и сравнение с baseline; имитация не принимается |

AC05–AC06 на синтетике проверяют алгоритм, но не доказывают качество на реальных stockout
и клиентах. AC04 на короткой реальной истории дополняется синтетической проверкой.

## Последующие этапы

IEK, точные stockout и клиентские признаки, интеграции Kaspi/1С/UMAG, рыночные признаки,
оценка реальных сроков поставок, общий бюджетный оптимизатор, несколько складов и
поставщиков, автоматическое переобучение и сравнение кандидата с действующей моделью.
