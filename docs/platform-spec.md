# Команда 1: ТЗ платформы

## Ответственность и объём

Команда отвечает за пользовательский интерфейс, клиент API, обработку состояний,
удобство проверки рекомендаций и совместную интеграцию. Расчёт спроса, заказа,
экономического эффекта и проверка ограничений выполняются бэкендом.

Предлагаемый стек при отсутствии существующего приложения: React + TypeScript + Vite.
Это предложение для четырёхчасового MVP; при наличии готового шаблона команда вправе
использовать его, сохранив HTTP-контракт. Создать `frontend/`.

## Экран 1: данные и запуск

- Поставщик: Systeme Electric. IEK показывать только при фактической поддержке backend.
- Загрузка нескольких XLSX, до шести обязательных ролей. ZIP и универсальное распознавание
  произвольного Excel не входят в MVP. Ограничения берём из `/health`.
- Отчёт импорта: роли файлов, дата данных, число позиций, ошибки, предупреждения,
  отсутствующие параметры и несопоставленные товары.
- Настройки: дата расчёта, поддерживаемый горизонт, срок поставки, период пересмотра,
  режим `operational/scenario`, профиль индивидуальных экономических параметров.
- Выбор склада/категории обязателен. Категориальная политика и прогноз прироста
  отображаются явно. Дополнительный нормализованный JSON-контекст загружается рядом
  с XLSX; формат и ошибки проверяет backend.
- У каждого вручную введённого параметра видны источник и основание. Для сценарных
  значений явная пометка, без оформления как фактической маржи.
- Запуск расчёта доступен после успешного импорта и базовой проверки настроек.

## Экран 2: рекомендации

Обязательные колонки: товар/код, категория, свободный остаток, своевременное поступление,
прогноз на горизонт, рекомендуемое количество, срочность, причина, статус данных/проверки.
Показывать единицы измерения. Не складывать метры, штуки и упаковки в один показатель.

Добавить уровень остатка: доступно / целевой запас и процент, пороги 40/30/20%
по индивидуальной политике. После события сразу обновлять строку и показывать сигнал
при ухудшении; не ждать ML/LLM. При потере связи отмечать устаревшее состояние.
Правила и симуляция: [stock-monitoring.md](stock-monitoring.md).

Группировка по поставщикам обязательна, даже если основной реальный набор содержит одного.
Фильтры на клиенте: поставщик, срочность, требуется проверка, поиск по коду/названию.
Блоки: «К закупке», «Закупка не требуется», «Недостаточно данных/нужна проверка».
`null` показывать как отсутствие расчёта с причиной; число `0` — как реальное решение.

Над таблицей: дата источников, версия набора, версия модели, метод (`ml/baseline`),
режим расчёта и версия правил. Сумма заказа показывается только при наличии необходимых
цен по всем включённым позициям; иначе выводится полнота оценки, а не ложный полный итог.

## Экран 3: карточка товара / боковая панель

- История продаж и прогноз. Если переданы только агрегаты, не рисовать выдуманную
  ежедневную траекторию. Интервал маркировать как прогнозный и указывать горизонт.
- Факты расчёта: доступный запас, резервы, поступления с ETA, прогноз, выбранный
  квантиль, партии и итог. Ссылки на файл/лист/строку либо ID факта в отчёте.
- Индивидуальный профиль: underage_cost, overage_cost, стоимость партии, источник параметров.
- Если экономики нет, показать policy_basis=service_policy и явно заданный квантиль;
  не скрывать базовую рекомендацию и не выдумывать прибыль.
- Предупреждения: неполный период, неизвестная доступность, мало истории, ограничения поставщика.
- ИИ: вывод, причины, использованные evidence_id/rule_id; либо явная причина недоступности.
- Корректировка количества и обязательное поле причины; серверная ошибка остаётся рядом с полем.

## Действия и состояния

- Импорт и расчёт асинхронны: `queued → running → succeeded/failed`.
- Polling `/jobs/{id}` примерно раз в 2 секунды. После завершения прекращать polling.
  При закрытии/переключении запроса отменять клиентское ожидание, не смешивать результаты задач.
- Состояния: пусто, загрузка, ошибка файла, предупреждения, расчёт, успех, недоступный backend,
  недоступный LLM, устаревшая версия редактирования, превышение бюджета, неподдержанный горизонт.
- Кнопку запуска защищать от повторного клика, сохраняя Idempotency-Key одной операции.
- Утверждение доступно после серверной проверки. При 409 обновить данные и показать конфликт.
- После успешного утверждения скачать CSV по approval_id; последующее редактирование
  создаёт новую ревизию и не меняет старый утверждённый снимок.
- В интерфейсе нет кнопки автоматической отправки заказа поставщику.

## Работа без готового backend

Использовать файлы `contracts/examples/` через изолированный mock-адаптер.
При использовании примеров постоянно показывать «Синтетический пример интерфейса».
Реальный режим включается переменной окружения адреса API; mock нельзя включать
автоматически при ошибке сети. Реальные ответы и синтетические примеры не смешивать.

Контракт примеров описывает только форму, а не обученную модель. UI должен быть готов
к дополнительным позициям и к нулевому списку рекомендаций.

## Готовность команды 1

1. Приложение запускается по инструкции из `frontend/README.md` с описанным адресом API.
2. Все три экрана работают с примерами и с фактическим API.
3. Ошибки и `null` не отображаются как успешное решение/нулевой спрос.
4. Пройден реальный сценарий корректировка → утверждение → CSV.
5. Режим, происхождение параметров и возраст данных видны на основном экране.
6. Нет формул закупки и экономических правил, продублированных в браузере.
7. Проверен экран на обычном ноутбуке; можно найти и объяснить одну рекомендацию без
   просмотра логов и технических идентификаторов.
